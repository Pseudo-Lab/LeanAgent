먼저, 무엇을 하는 프로젝트인가?

Strata는 프로그램의 문법과 의미를 정의하고, 그 프로그램을 자동 검증하는 Lean4 기반 프레임워크입니다. 여러 언어를 다룰 수 있도록 중간 표현으로의 변환을 제공합니다. Strata 공식 소개

검증 도구는 복잡한 프로그램을 분석하기 쉬운 형태로 바꾸기도 합니다. 그런데 바꾸는 도구 자체가 실수하면, 원래 프로그램에 대한 결론도 믿기 어려워집니다. 그래서 변환 코드가 필요한 성질을 지키는지도 Lean으로 증명합니다. Lean은 작성한 증명이 명제를 만족하는지 검사합니다.

이번에 보는 부분: 함수 호출을 다루기 쉽게 바꾸기

대상 파일의 call elimination은 함수 호출을 계약에 기반한 더 기본적인 명령으로 바꾸는 변환을 다룹니다. 계약은 “호출 전에 필요한 조건”과 “호출 후에 보장하는 조건”입니다. 호출 후 조건에서 쓰는 old(balance)는 호출 직전의 잔액을 뜻합니다.

호출 후 조건에서 old 찾기→ 이전 값을 저장할 변수 준비→ old를 저장 변수로 치환

예를 들어 호출 전 잔액이 10이고 호출 후 13이면, balance = old(balance) + 3은 13 = 10 + 3이라는 뜻입니다. 이전 값을 saved_balance에 저장해 두면 조건식의 old 부분을 그 변수로 바꿔 표현할 수 있습니다.

원래 프로젝트에 왜 필요한 정리인가?

이름을 추출하거나 식을 바꿀 때, 변환 결과에 엉뚱한 변수 이름이 끼어들지 않는다는 보조 성질이 필요합니다. 1·2번은 이 변수 이름 관리를 증명하는 작은 부품입니다. 두 정리만으로 변환 전체의 의미 보존을 증명하지는 않습니다. 우리의 과제는 같은 명제를 증명하면서 반복을 줄이고 읽기 좋은 구조로 고치는 것입니다. 이 두 문제는 AST의 경우 분석과 목록 포함 관계가 반복되어, 공통 처리와 귀납 대상 선택을 연습하기 좋습니다. 이는 이 사례를 공부하는 이유에 대한 설명입니다.

용어 정리

bvar: bound variable, fvar: free variable.

∑ k = 1 10 ( k + a )
여기서 k가 bvar, a는 fvar에 해당합니다. const: 전역에 정의된 상수, lit: literal. 컴파일러가 바로 인식하는 값, op: operation, abs: 추상화, quant:quantifier, eq: equality, ite: if-then-else, cih, tih, eih: 조건식 자체가 성립하는지 판정하는 근거나 then/else분기 안에서 쓸 수 있는 가설

변환 알고리즘을 빠르게 만드는 작업과, 그 성질을 보이는 증명 코드를 고치는 작업은 별개입니다. 여기서는 증명 코드를 고칩니다. 실습은 Lean v4.26.0과 Strata revision 451e5f0입니다.

AST와 순회: 식을 나무로 보고 따라가기

AST(Abstract Syntax Tree, 추상 구문 트리)는 식의 논리 구조를 나무 형태의 데이터로 나타낸 것입니다. ∀ x, if x = 0 then 1 else x + a 같은 명제를 보면, 바깥쪽의 한정자(quant)부터 안쪽의 조건 분기(ite)와 등식(eq), 그리고 묶인 변수(bvar)와 열린 변수(fvar)까지 계층적으로 연결됩니다.

이해를 위한 단순화된 나무

quant (∀ x)
└─ ite (조건 분기)
   ├─ eq (조건식: =)
   │  ├─ bvar (x)
   │  └─ lit (0)
   ├─ then (tih: x = 0 가설)
   │  └─ lit (1)
   └─ else (eih: x ≠ 0 가설)
      └─ op (+)
         ├─ bvar (x)
         └─ fvar (a)

순회(traversal)는 나무의 노드를 일정한 규칙으로 방문하는 일입니다. 방문하면서 자유 변수나 가설을 수집할 수도 있고, 특정 형태의 부분식을 찾아 재작성할 수도 있습니다.

아래 순회에서는 위에서 시작해 조건부부터 차례로 방문합니다. 현재 문맥에 바깥에서 주어진 자유 변수(fvar)만 모으면 [a]를 얻습니다. 바인더에 묶인 x는 임시 파라미터(bvar)이므로 전역 자유 변수 목록에 넣지 않습니다.

방문 전 · 모은 자유 변수: []

주요 생성자 역할:
• quant: 변수를 한정짓는 바인더(∀, ∃)로, 내부의 x를 bvar(바운드 변수)로 묶습니다.
• ite: 조건에 따라 분기하는 식으로, 조건(eq)과 참/거짓 분기를 가집니다.
• tih / eih: then/else 분기 내부에서 사용할 수 있는 조건의 참/거짓 가설(Hypothesis) 정보입니다.
• fvar: 바깥 로컬 컨텍스트에 이미 존재하는 독립된 자유 변수(a)입니다.

순회와 귀납은 어떻게 연결될까?

순회 함수는 큰 식을 작은 식(하위 트리)으로 나누어 처리합니다. 구조 귀납은 그 함수의 성질을 증명할 때, “조건식, then 분기, else 분기 등 하위 노드에서 성질이 성립한다고 가정하고, 이를 조립한 ite 전체에서도 성립함”을 보이는 방법입니다.

예를 들어 then 분기에서 수집한 자유 변수와 else 분기에서 수집한 변수가 각각 유효 범위 안에 있다면, 이들을 합친 목록 전체도 유효 범위 안에 들어옵니다. 이 구조적 재귀 논리가 바로 Expr 귀납 증명의 핵심입니다.

같은 예제로 이해하는 Warm-up 1·2

이 두 문제는 “프로그램 식을 바꿔도 예상 못 한 변수 이름이 생기지 않는다”를 확인하는 작은 안전장치입니다.

이제 예제를 x = old(y) + z로 고정해 봅시다. 2번은 여기에서 저장할 값의 이름 y를 추출하는 단계, 1번은 old(y)를 저장 변수 saved_y로 치환하는 단계에 해당합니다. 처리 흐름으로는 추출을 먼저 이해하면 자연스럽습니다.

getVars는 값이 아니라 식에 쓰인 자유 변수의 이름 목록을 모읍니다. Subset은 “왼쪽에 있는 이름은 모두 오른쪽에도 있다”입니다. 순서와 반복 횟수는 비교하지 않습니다.

1번 · 치환의 안전장치

old(h2)를 변수 h1으로 바꾸면, 결과 변수는 원래 있던 변수 또는 h1입니다.

x = old(y) + z
↓ old(y)를 saved_y로 교체
x = saved_y + z

결과에 허용되는 이름은 원래 이름에 saved_y를 더한 목록입니다. 이것이 정리 오른쪽에 ++ [h1]이 있는 이유입니다.

풀이: 작은 식마다 이름 범위가 지켜진다고 가정합니다. 두 결과를 합쳐도 범위가 지켜진다는 combine을 한 번 증명하고, 여러 부분 식을 가진 경우마다 재사용합니다.

2번 · 추출의 안전장치

old가 규칙에 맞게 쓰였을 때, old 안에서 뽑은 이름은 원래 식에도 있습니다.

x = old(y) + z
old에서 뽑은 이름: [y]
전체 이름: [x, y, z]

추출 함수는 old(변수) 모양을 기대합니다. 직접 old(x + y)를 받는 경우를 제외하는 정규화 증거가 필요합니다.

풀이: “old가 규칙에 맞게 쓰였다”는 증거에 귀납합니다. 부분 식의 결과는 combine으로 합치고, old의 인수가 잘못된 경우는 정규화 조건으로 제외합니다.

이 정리가 보장하지 않는 것도 확인하기

1번에는 정규화 가정이 없습니다. 치환 뒤의 이름 범위만 보장하며, saved_y가 다른 이름과 충돌하지 않는지 또는 올바른 이전 값을 담고 있는지는 별도 조건이 필요합니다. old(y) + y에서 바뀌는 것은 old 부분뿐입니다.

2번은 NormalizedOldExpr라는 정규화 증거를 가정합니다. old가 적용되는 곳의 인수는 자유 변수여야 합니다. 예를 들어 old(y + z)는 그대로 추출하는 입력이 아니고, 정규화 과정을 거쳐야 합니다. 추출 함수의 잘못된 입력 분기에는 panic!이 있습니다.

Subset은 포함 관계입니다. [y, y] ⊆ [y]도 성립하므로 이름의 중복 횟수나 순서를 보장한다는 뜻은 아닙니다. “새 이름이 없다”는 사실만으로 “식의 값도 같다”가 따라오지는 않습니다.

증명 아이디어를 코드 없이 읽으면

상수나 일반 변수는 그대로이므로 이름 범위도 그대로입니다. old(h2)가 실제로 바뀌면 새 이름은 h1 하나뿐입니다. 큰 식에서는 부분 식들의 결과를 합칩니다.

예를 들어 왼쪽 부분 식의 결과 이름이 “원래 왼쪽 이름 + h1” 안에 있다는 귀납 가설을 얻었다고 합시다. 이 허용 범위는 “원래 전체 이름 + h1” 안에도 들어갑니다. 오른쪽에도 같은 논리를 적용하면 전체 결과가 허용 범위에 들어갑니다. 새 코드에서는 combine이 이 연결을 담당합니다.

Lean으로 쓴 정확한 명제

CallElimCorrect.lean
open OldExpressions in
theorem substOldPostSubset:
  (Imperative.HasVarsPure.getVars (P:=Expression)
    (substOld h2 (Lambda.LExpr.fvar m h1 ty) post)).Subset
    (Imperative.HasVarsPure.getVars (P:=Expression) post ++ [h1])

open OldExpressions in: 바로 다음 theorem에서만 OldExpressions 네임스페이스의 이름들을 접두사 없이 쓰겠다는 뜻.

substOld h2 (fvar m h1 ty) post: post 안의 old(h2)를 free variable h1(타입 ty, 메타데이터 m)로 치환한 결과 식.

getVars e: 식 e에 등장하는 변수들의 리스트.

A.Subset B: 리스트 포함 관계. 즉 ∀ v, v ∈ A → v ∈ B.

코드의 흐름

① 목록 결합 성질 → ② 식에 대한 귀납 → ③ old 적용만 별도 처리. combine의 a·b는 변환 결과의 이름 목록이고, c·d는 원래 부분 식의 이름 목록입니다. a의 이름은 c 또는 h1에, b의 이름은 d 또는 h1에 있으면, 합친 결과의 이름도 c·d 또는 h1에 있습니다.

상수·연산자는 빈 목록, 일반 변수는 원래 목록 안에 있습니다. abs는 부분 식의 귀납 가설을 그대로 쓰고, quant·eq는 combine 한 번, 세 부분 식을 가진 ite는 두 번 사용합니다. app에서는 old(h2)가 치환되면 새 이름이 오른쪽 목록 [h1]에, 유지되면 이름이 왼쪽의 원래 목록에 포함됨을 직접 보입니다. 일반 적용은 다시 combine을 씁니다.

왜 식보다 정규화 증거에 귀납할까?

등식이 정규화됐다는 증거는 왼쪽과 오른쪽이 각각 정규화됐다는 증거로 만들어집니다. 따라서 이 증거를 따라 귀납하면, 두 부분 식의 정규화 증거와 “추출한 이름은 그 부분 식에 있다”는 귀납 가설을 함께 얻습니다.

old(y) 분기에서는 추출 결과가 [y]이고 전체 변수 목록에도 y가 있습니다. 나머지 재귀 분기에서는 부분 식의 포함 관계를 합칩니다. old의 인수가 자유 변수가 아닌 분기는 정규화 증거의 조건과 모순입니다. 식에 먼저 귀납하던 원본도 맞지만, 이 조건을 분기마다 다시 꺼내야 했습니다.

코드의 흐름

① 목록 결합 성질 → ② 정규화 증거에 대한 귀납 → ③ old의 모양 확인. 여기서 combine은 “a의 이름은 c에 있고 b의 이름은 d에 있으면, a++b의 이름은 c++d에 있다”입니다.

app 분기에는 세 경우가 있습니다. old(변수)이면 추출한 이름은 이미 원래 식에 있습니다. old의 인수가 자유 변수가 아닌 경우에는 hold .oldPred가 주는 증거와 모순입니다. 일반 함수 적용이면 두 귀납 가설을 combine으로 합칩니다. 불가능한 경우를 제외하는 논리를 코드에서 직접 볼 수 있습니다.
