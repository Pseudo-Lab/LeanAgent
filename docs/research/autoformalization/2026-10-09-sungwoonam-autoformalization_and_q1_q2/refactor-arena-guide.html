01 · What is autoformalization?

Autoformalization은
수학 글을 형식 언어로 옮기는 작업입니다.

자연어 수학“두 짝수의 합은 짝수다.”
증명: 두 수를 2의 배수로 쓰자.
→
형식적 진술대상은 정수인가?
짝수의 정의는 무엇인가?
‘모든’인가, ‘어떤’인가?
→
형식적 증명정확한 중간 주장과 증명 항을 만들고 Lean이 검사한다.
작업입력 → 출력성공 판단
Statement autoformalization자연어 명제 → Lean 명제잘 정의됨 + 원래 의미 보존
Proof autoformalization자연어 증명 → Lean 증명정리 증명 성공 + 요구한 증명 경로의 충실성
Automated theorem proving고정된 Lean 명제 → Lean 증명주어진 명제를 kernel이 승인

정의·구분: Wu et al., 2022 [R1], Weng et al., Survey, 2025 [R4]. 용어의 범위는 논문마다 다르므로 입력·출력을 함께 확인합니다.

용어 정리넓은 의미의 autoformalization은 진술과 증명 둘 다 포함합니다. 그런데 특정 논문에서 autoformalization 정확도라고 하면 증명 없이 statement만 번역한 성적일 수 있습니다. Arena에서는 고정된 명제에 대한 재증명도 가능하므로, 원래 증명 경로를 그대로 따를 필요는 없습니다.
01 · Example / High-school mathematics

“두 짝수의 합은 짝수다.”

사람이 생략한 정보

대상: 정수 a, b

짝수의 뜻: 정수 k가 있어서 n = 2k

가정: a = 2u, b = 2v인 정수 u, v가 존재

결론: a + b = 2w인 정수 w가 존재

a + b = 2u + 2v = 2(u + v)

w = u + v로 선택하면 됩니다.
이처럼 존재 조건을 만족하도록 제시하는 값을 논리학에서 증인(witness)이라고 합니다.

형식적 증명 예시

import Mathlib

example (a b : ℤ)
    (ha : ∃ u : ℤ, a = 2 * u)
    (hb : ∃ v : ℤ, b = 2 * v) :
    ∃ w : ℤ, a + b = 2 * w := by
  rcases ha with ⟨u, hu⟩
  rcases hb with ⟨v, hv⟩
  refine ⟨u + v, ?_⟩
  rw [hu, hv]
  ring

교육용 Lean 4 예시. 이 문서에서 실제 Mathlib 환경으로 컴파일하지는 않았습니다. ?_는 뒤의 전술이 해결할 목표이고, 완료된 증명의 구멍을 뜻하지 않습니다.

코드 읽는 법ℤ는 정수, ∃는 존재한다는 뜻입니다. rcases는 “존재한다”의 증인을 꺼내고, refine은 우리가 선택한 증인을 넣습니다. rw는 등식으로 바꿔 쓰고 ring은 남은 다항식 항등식을 증명합니다. 이 짧은 예시에도 번역과 증명 생성이 분리되어 있습니다.
01 · Interactive / Meaning preservation

컴파일되어도,
의도한 statement가 아닐 수 있습니다.

“정수 n이 짝수다”를 어떻게 옮길까요?

후보의 수학적 의미
∃ k ∈ ℤ, n = 2k
∃ k : ℤ, n = 2 * k

Lean 표현의 타입 적합성과 자연어 대응은 서로 다른 검사입니다.

n = 3을 넣어 보면?

컴파일은 표현의 타입이 맞는지 확인합니다. 그 표현이 “짝수”를 뜻하는지는 별도로 확인해야 합니다.

Arena에서는 이 위험을 줄일 수 있습니다. 원래 진술을 보존하고 새 증명 본문만 붙입니다.
관객 참여유리수 증인을 선택하면 3 = 2 × 1.5여서 모든 정수에 대해 참이 됩니다. 타이핑 오류가 아니라 의미 오류입니다. ‘모든 k’로 바꾸는 경우는 훨씬 강한 거짓 명제가 됩니다. 이 시연은 브라우저의 설명 전환이며 실제 Lean 검사를 실행하지 않습니다.
01 · 선형대수 예시

선형 독립 증명에 기존 lemma를 적용하기.

문제: u = (1, 0), v = (0, 1)이 ℝ²에서 선형 독립임을 증명하라.

직접 증명하면

au + bv = (0, 0)
⇒ (a, b) = (0, 0)
⇒ a = 0, b = 0

이것이 선형 독립의 조건입니다. 모든 실수 a, b에 대해 이 결론이 나와야 합니다.

Lean에서도 벡터 등식의 첫 좌표와 둘째 좌표를 꺼내 각각 a = 0, b = 0을 확인할 수 있습니다.

Mathlib의 기존 정리를 쓰면

linearIndependent_fin2는 두 벡터의 선형 독립을 다음 두 조건으로 바꿉니다.

① v ≠ 0
② 어떤 실수 c를 곱해도 cv ≠ u

example : LinearIndependent ℝ
    (![ (1, 0), (0, 1)] :
      Fin 2 → ℝ × ℝ) := by
  rw [linearIndependent_fin2]
  constructor
  · simp
  · intro c h
    have hx := congrArg Prod.fst h
    simpa using hx

②에서는 cv의 첫 좌표가 0, u의 첫 좌표가 1이라 모순입니다. Fin 2는 두 벡터에 붙인 인덱스입니다.

리팩터링 아이디어: 수학적으로 어떤 성질을 증명하는지 파악한 뒤, 같은 성질을 다루는 기존 lemma를 찾습니다. 여기서는 일반적인 선형 독립 조건을 처음부터 풀어 쓸 필요가 없습니다.

실제 정리: Mathlib: linearIndependent_fin2. 위 완전한 예시는 import Mathlib 문맥을 전제로 하며 이 환경에서 컴파일하지 않았습니다. 길이·비용 개선은 측정하지 않았습니다.

설명 순서먼저 왼쪽 수학 증명을 읽습니다. have는 중간 사실을 기록하는 Lean 문법입니다. “좌표별 have를 반복한다”는 추상적인 표현 대신 실제로 첫 좌표와 둘째 좌표에서 무엇을 얻는지 보여줍니다. 오른쪽은 정의를 외우라는 뜻이 아니라 같은 명제를 이미 다루는 라이브러리 정리를 이용하자는 예시입니다. 기존 lemma도 마지막의 쉬운 좌표 확인까지 자동으로 없애주지는 않습니다.
01 · 확률 예시

Lean에서 A와 B를 따로 선언해도
독립인 사건이 되지는 않습니다.

원문: “독립인 두 사건 A, B에 대해 P(A ∩ B) = P(A)P(B).”

잘못된 번역: 독립성 가정 누락

-- 확률측도 μ 등의 공통 환경은 생략
(A B : Set Ω) :
    μ (A ∩ B) = μ A * μ B

A B : Set Ω는 “사건 두 개”만 뜻합니다. A ≠ B나 독립성은 포함하지 않습니다.

이 진술은 B = A도 포함합니다.

동전 한 번의 앞면 사건 A라면:
A ∩ A = A, 따라서 왼쪽은 ½.
오른쪽은 ½ × ½ = ¼.

그러므로 이 일반 명제는 거짓입니다.

의도한 번역: 독립성을 명시

-- ProbabilityTheory namespace 문맥
(A B : Set Ω)
(h : IndepSet A B μ) :
    μ (A ∩ B) = μ A * μ B

IndepSet A B μ가 원문의 “독립인”에 해당합니다.

이 가정이 있으면 기존 lemma로 증명할 수 있습니다.

by
  exact h.measure_inter_eq_mul

μ는 Mathlib의 측도로 확률을 표현합니다. 코드는 전체 declaration 대신 핵심 인자·결론·증명 본문을 보여주는 발췌입니다.

B = A는 임의로 추가한 상황이 아니라, 빠진 가정 때문에 잘못 번역된 진술이 허용하는 반례입니다. Lean에서는 잘 정의된 거짓 명제도 표현할 수 있습니다.

정의와 정리: Mathlib: IndepSet.measure_inter_eq_mul. 가정 없는 statement의 타입 적합성과 완성된 proof의 승인 여부는 다릅니다.

왜 A=B를 보는가?수학에서 서로 다른 변수 이름을 쓴다고 서로 다른 값이라는 뜻은 아닙니다. 예를 들어 a, b : ℝ도 a=b일 수 있습니다. A B : Set Ω 역시 마찬가지입니다. 독립성 없이 두 사건을 선언한 진술에는 같은 사건도 대입할 수 있으므로 반례가 됩니다. A≠B만 추가해도 충분하지 않습니다. 서로 다른 사건도 종속일 수 있습니다. 원문에 있던 독립성만 충실히 옮겨야 하며, 원문에 없으면 임의로 추가하면 안 됩니다. 거짓 명제의 proof body를 sorry로 채운 compile은 실제 증명이 아닙니다.

숫자 발표의 포인트Pass@128은 128개 중 성공하는 후보가 있는지 보는 지표입니다. 일반 사용자가 한 번 받아보는 결과의 신뢰도와 다릅니다. 또한 번역 성공, 고정된 정리의 증명 성공, 증명 리팩터링의 점수 향상은 서로 다른 작업입니다. 이 가이드의 조사 기준일은 2026-10-09이며 아래 2026 논문은 공개 preprint 기준으로 소개합니다.

왜 이런 차이가 생길까?

앞의 예처럼 증인의 타입이나 독립성 가정을 잘못 옮겨도 statement는 잘 정의될 수 있습니다.

Compiler feedback은 문법·타입 오류를 고치는 데 도움이 됩니다. 그러나 빠진 독립성 같은 의미 오류를 찾아주지는 않습니다.

Arena 해석
기존 진술·정의·환경이 있는 Arena에서는 이를 보존해 번역 위험을 줄입니다. 남는 문제는 전략 선택과 최적화입니다.

출처: Beyond Compilation, §4–5 [R7, 2026 preprint]. 의미 통과는 GPT/Gemini consensus와 사람 보정에 기반하며 formal equivalence 인증은 아닙니다. 이 표는 분야 전체의 보편적 정확도를 나타내지 않습니다. 최신 관련 연구: FaithformBench [R8]는 틀린 입력을 번역기가 조용히 고쳐 버리는 문제도 다룹니다.

오해를 막기컴파일하는 진술에 sorry가 붙어 있는 statement-only benchmark이므로 89.5%를 “증명을 89.5% 풀었다”로 말하면 안 됩니다. Consensus에서 떨어진 모든 사례가 확정적인 의미 오류라는 뜻도 아닙니다. 연구는 별도 사람 표본 감사로 지표를 보정했습니다.

바꿔볼 것

계산 순서, 중간 주장, 경우 나누기, 적용할 lemma입니다. 예를 들어 “이 계산 전체가 다항식 항등식”임을 알면 다른 증명을 찾을 수 있습니다.

새 proof body를 원래 정리 진술에 붙여 검사합니다. 컴파일에 성공한 후보만 길이·heartbeats·버전 호환성으로 비교합니다.

근거가 되는 선행 접근: DSP [R2], Lean Refactor [R10]. 이 왕복 경로의 Arena 점수 향상은 별도 ablation으로 검증해야 합니다.

사용자의 아이디어에 대한 답네, formal → natural language → 새 풀이 → formal 경로는 시도할 가치가 있습니다. 다만 원래 theorem을 자연어로만 전달해서 새 theorem으로 제출하는 것이 아니라, 원래 formal target을 보존한 채 증명 전략을 재설계하는 방식으로 구현해야 합니다.
03 · Worked refactoring example / High-school algebra

예시: 제곱 전개 증명을
한 번의 항등식 증명으로 줄이기.

(a + b)² = a² + 2ab + b²   (a, b ∈ ℝ)

Before · 전개 단계를 모두 기록

example (a b : ℝ) :
    (a + b)^2 = a^2 + 2*a*b + b^2 := by
  calc
    (a + b)^2 = (a + b)*(a + b) := by
      rw [pow_two]
    _ = a*(a + b) + b*(a + b) := by
      rw [add_mul]
    _ = (a*a + a*b) + (b*a + b*b) := by
      rw [mul_add, mul_add]
    _ = a^2 + 2*a*b + b^2 := by
      ring

수학적 설명 → After

“모든 실수에 대한 다항식 항등식이다. 가정 없이 정규화로 증명할 수 있다.”

example (a b : ℝ) :
    (a + b)^2 = a^2 + 2*a*b + b^2 := by
  ring

후보 기존 calc 전체를 항등식 증명으로 대체합니다.

두 코드 모두 import Mathlib 문맥을 전제로 한 교육용 예시이며 여기서 Lean 컴파일은 실행하지 않았습니다. 실제 비용·버전 이득도 측정하지 않았습니다.

본문이 짧아지는 후보를 얻었습니다. 하지만 ring이 더 싼지, 지정 버전에서 모두 통과하는지는 실제로 측정해야 합니다.
이 예시의 정직한 범위코드를 몇 줄 줄였는지와 heartbeat를 얼마나 줄였는지는 다릅니다. before도 마지막에 ring을 사용하지만 앞의 계산 과정이 필요 없음을 알아낸 것이 핵심입니다. 실제 Arena의 수천 토큰 증명에는 이보다 복잡한 라이브러리와 의존성이 있습니다.

03 · Experimental plan Warm-up 실험 제안

다음 실험: 자연어 재설계가
직접 리팩터링보다 도움이 될까요?

조건허용할 작업알고 싶은 것
A · Direct baseline원래 Lean proof → 직접 리팩터링 + compiler feedback자연어 재설계 없이 얻는 개선
B · ExplanationA + 블록별 수학 설명설명 자체가 구조 파악에 도움이 되는가?
C · RedesignB + 새로운 자연어 proof sketch → Lean증명 경로를 바꾸면 추가 개선이 생기는가?
D · RetrievalC + 버전별 lemma/전략 검색설명의 효과와 검색 효과를 분리할 수 있는가?

통제

같은 모델·버전·문제·context, 전체 LLM 및 Lean 호출 예산을 맞춥니다. 가능하면 여러 seed로 반복합니다.

쉬운 문제만 골라 평균을 내지 않고, 실패·무개선도 전체 분모에 넣습니다.

기록

진술 보존·compile 성공 → 토큰·heartbeats·호환 버전 → 공식 combined score.

별도 기록: LLM 비용·시간, 새 lemma 수, 전략 종류, 실패 단계.

발표의 결론: 원래 정리를 고정하고, 새 증명 방법을 찾고, 통과한 후보의 세 가지 성능을 측정합니다. 자연어 단계를 넣을지는 이 비교 실험으로 판단합니다.
실험 결과를 읽는 법D가 가장 좋다고 해서 자연어 단계가 원인이라고 결론 내리면 안 됩니다. 여력이 있으면 A+retrieval도 추가해 검색만의 효과를 확인합니다. 후보 생성 비용이 다른 실험은 matched budget과 무제한 성능을 각각 보고합니다. Warm-up은 개발용이고 공개 문제 과적합이 본 benchmark 성능으로 이어진다고 가정하지 않습니다.
