01 · What is autoformalization?

Autoformalization은
Mathematical statements를 컴퓨터가 이해할 수 있는 언어(Lean4 등)으로 옮기는 작업입니다.

자연어 수학“두 짝수의 합은 짝수다.”
증명: 두 수를 2의 배수로 쓰자.
→
형식적 진술대상은 정수인가?
짝수의 정의는 무엇인가?
‘모든’인가, ‘어떤’인가?
→
형식적 증명정확한 중간 주장과 증명 항을 만들고 Lean이 검사한다.
작업입력 → 출력성공 판단
Statement autoformalization자연어 명제 → Lean 명제잘 정의됨 + 원래 의미 보존
Proof autoformalization자연어 증명 → Lean 증명정리 증명 성공 + 요구한 증명 경로의 충실성
Automated theorem proving고정된 Lean 명제 → Lean 증명주어진 명제를 kernel이 승인
용어 정리넓은 의미의 autoformalization은 진술과 증명 둘 다 포함합니다. 그런데 특정 논문에서 autoformalization 정확도라고 하면 증명 없이 statement만 번역한 성적일 수 있습니다. Lean Refactor Arena에서는 고정된 명제에 대한 재증명도 가능하므로, 원래 증명 경로를 그대로 따를 필요는 없습니다.
01 · 자연어 증명을 Lean으로 옮기기

“두 짝수의 합은 짝수다.”

암묵적인 가정

대상: 정수 a, b

짝수의 뜻: 정수 k가 있어서 n = 2k

가정: a = 2u, b = 2v인 정수 u, v가 존재

결론: a + b = 2w인 정수 w가 존재

a + b = 2u + 2v = 2(u + v)

w = u + v로 선택하면 됩니다.
이처럼 존재 조건을 만족하도록 제시하는 값을 논리학에서 증인(witness)이라고 합니다.

형식적 증명 예시

import Mathlib

example (a b : ℤ)
    (ha : ∃ u : ℤ, a = 2 * u)
    (hb : ∃ v : ℤ, b = 2 * v) :
    ∃ w : ℤ, a + b = 2 * w := by
  rcases ha with ⟨u, hu⟩
  rcases hb with ⟨v, hv⟩
  refine ⟨u + v, ?_⟩
  rw [hu, hv]
  ring

refine ⟨u + v, ?_⟩는 w로 u + v를 선택합니다. ?_ 자리에 필요한 것은 a + b = 2 * (u + v)의 증명입니다.

rw [hu, hv]로 a = 2u, b = 2v를 대입하고, ring으로 등식을 증명합니다.

교육용 Lean 4 예시. 이 문서에서 실제 Mathlib 환경으로 컴파일하지는 않았습니다.

코드 읽는 법ℤ는 정수, ∃는 존재한다는 뜻입니다. rcases는 “존재한다”의 증인을 꺼내고, refine은 우리가 선택한 증인을 넣습니다. rw는 등식으로 바꿔 쓰고 ring은 남은 다항식 항등식을 증명합니다. 이 짧은 예시에도 번역과 증명 생성이 분리되어 있습니다.
01 · Mistranslation

컴파일되어도,
의도한 statement가 아닐 수 있습니다.

① 정수 대신 유리수를 쓰면

원래 의미: “정수 n이 짝수다.”

-- 올바른 표현
∃ k : ℤ, n = 2 * k
-- 잘못 옮긴 표현
∃ k : ℚ, (n : ℚ) = 2 * k

두 번째 표현에서는 n = 3도 k = 3/2로 만족합니다. ‘짝수’라는 조건이 사라졌습니다.

② 독립이라는 가정을 빼면

원래 의미: “독립 사건 A, B에 대해
P(A ∩ B) = P(A)P(B).”

-- 독립 가정이 빠진 명제
(A B : Set Ω) :
  μ (A ∩ B) = μ A * μ B
-- 필요한 가정
(h : IndepSet A B μ)

Lean은 A와 B가 서로 다르다고 자동으로 가정하지 않습니다. B = A, P(A) = 1/2이면 왼쪽은 1/2, 오른쪽은 1/4입니다.

위 코드는 진술의 일부입니다. 타입이 맞아 Lean이 명제를 받아들이는 것과, 그 명제가 참이거나 원래 의미와 일치하는 것은 별개입니다. 독립 가정을 빠뜨린 일반 명제는 증명할 수 없습니다.

Lean Refactor Arena에서는 원래 진술을 보존하고 증명만 바꿉니다.

관련 읽기: Navier-Stokes lost in translation: Why Lean verification of AI autoformalisation does not guarantee correct natural language proofs [R13, 2026-10 preprint]. 자연어와 형식화된 명제 사이의 불일치를 다룹니다. 독립 가정: Mathlib: IndepSet.measure_inter_eq_mul.

두 오류의 차이첫 예시는 타입을 바꿔 조건을 약화한 경우입니다. 둘째는 가정 누락으로 거짓인 일반 명제를 만든 경우입니다. ‘컴파일된다’가 statement를 받아들이는 것인지, 완성된 증명까지 검사한 것인지 구분해 설명하세요. 두 예시는 이 가이드의 교육용 예시이며 Navier–Stokes 논문에서 가져온 사례가 아닙니다.
01 · 증명의 의미를 파악해 기존 정리 찾기

선형 독립 증명에 기존 lemma를 적용하기.

문제: u = (1, 0), v = (0, 1)이 ℝ²에서 선형 독립임을 증명하라.

직접 증명하면

au + bv = (0, 0)
⇒ (a, b) = (0, 0)
⇒ a = 0, b = 0

이것이 선형 독립의 조건입니다. 모든 실수 a, b에 대해 이 결론이 나와야 합니다.

Lean에서도 벡터 등식의 첫 좌표와 둘째 좌표를 꺼내 각각 a = 0, b = 0을 확인할 수 있습니다.

Mathlib의 기존 정리를 쓰면

linearIndependent_fin2는 두 벡터의 선형 독립을 다음 두 조건으로 바꿉니다.

① v ≠ 0
② 어떤 실수 c를 곱해도 cv ≠ u

example : LinearIndependent ℝ
    (![ (1, 0), (0, 1)] :
      Fin 2 → ℝ × ℝ) := by
  rw [linearIndependent_fin2]
  constructor
  · simp
  · intro c h
    have hx := congrArg Prod.fst h
    simpa using hx

②에서는 cv의 첫 좌표가 0, u의 첫 좌표가 1이라 모순입니다. Fin 2는 두 벡터에 붙인 인덱스입니다.

리팩터링 아이디어: 수학적으로 어떤 성질을 증명하는지 파악한 뒤, 같은 성질을 다루는 기존 lemma를 찾습니다. 여기서는 일반적인 선형 독립 조건을 처음부터 풀어 쓸 필요가 없습니다.

실제 정리: Mathlib: linearIndependent_fin2. 위 완전한 예시는 import Mathlib 문맥을 전제로 하며 이 환경에서 컴파일하지 않았습니다. 길이·비용 개선은 측정하지 않았습니다.

설명 순서먼저 왼쪽 수학 증명을 읽습니다. have는 중간 사실을 기록하는 Lean 문법입니다. “좌표별 have를 반복한다”는 추상적인 표현 대신 실제로 첫 좌표와 둘째 좌표에서 무엇을 얻는지 보여줍니다. 오른쪽은 정의를 외우라는 뜻이 아니라 같은 명제를 이미 다루는 라이브러리 정리를 이용하자는 예시입니다. 기존 lemma도 마지막의 쉬운 좌표 확인까지 자동으로 없애주지는 않습니다.

02 · Bottleneck / Statement generation

진술 번역의 주요 병목은
원래 의미를 정확히 옮기는 것입니다.

같은 400개 진술, 같은 full agent

Lean에서 compile89.5% · 358/400
의미 심사까지 통과60.5% · 242/400

차이: 116개, 29.0 percentage points.
형식적 증명 없는 statement-only 평가.

왜 이런 차이가 생길까?

앞의 예처럼 증인의 타입이나 독립성 가정을 잘못 옮겨도 statement는 잘 정의될 수 있습니다.

Compiler feedback은 문법·타입 오류를 고치는 데 도움이 됩니다. 그러나 빠진 독립성 같은 의미 오류를 찾아주지는 않습니다.

Lean Refactor Arena 해석
기존 진술·정의·환경이 있는 Lean Refactor Arena에서는 이를 보존해 번역 위험을 줄입니다. 남는 문제는 전략 선택과 최적화입니다.

출처: Beyond Compilation, §4–5 [R7, 2026 preprint]. 의미 통과는 GPT/Gemini consensus와 사람 보정에 기반하며 formal equivalence 인증은 아닙니다. 이 표는 분야 전체의 보편적 정확도를 나타내지 않습니다. 최신 관련 연구: FaithformBench [R8]는 틀린 입력을 번역기가 조용히 고쳐 버리는 문제도 다룹니다.

오해를 막기컴파일하는 진술에 sorry가 붙어 있는 statement-only benchmark이므로 89.5%를 “증명을 89.5% 풀었다”로 말하면 안 됩니다. Consensus에서 떨어진 모든 사례가 확정적인 의미 오류라는 뜻도 아닙니다. 연구는 별도 사람 표본 감사로 지표를 보정했습니다.
02 · Proof autoformalization / ToMap [R9]

증명 전체를 옮기는 작업을
세 역할로 나눕니다.

Decomposer · Formalizer · Prover는 ToMap 논문의 agent 역할 이름입니다.

Lean의 문법이나 모든 시스템이 따르는 표준 명칭은 아닙니다.

01 · DECOMPOSER

증명 분해

입력: 자연어 정리와 증명

출력: 작은 증명 단위와 의존 관계

각 주장에 필요한 가정을 명시하고, 어떤 주장을 먼저 증명해야 하는지 정합니다.

02 · FORMALIZER

주장의 형식화

입력: 각 증명 단위와 문맥

출력: Lean의 명제·목표

대상의 타입, 변수, 가정을 정해 자연어 주장을 정확한 형식적 진술로 옮깁니다.

03 · PROVER

목표의 증명

입력: 형식화된 목표

출력: 목표를 증명하는 Lean 코드

사용 가능한 가정과 기존 정리로 각 목표를 해결합니다.

Prover는 코드를 생성합니다. Lean은 그 코드가 목표를 증명하는지 검사합니다. 조립한 전체 증명도 다시 검사해야 합니다.

역할 정의: Efficient Test-Time Optimization for Multi-Agent Proof Autoformalization, §2.2 [R9, 2026-07 preprint].

02 · 세 역할을 예시에 대입하기

“두 짝수의 합은 짝수다”를
단계별로 옮겨봅시다.

문맥: a, b, u, v는 정수이며 hu : a = 2u, hv : b = 2v입니다.

Decomposer: 중간 주장 정하기

① a + b = 2(u + v)를 보인다.
② w = u + v로 선택해 존재 명제를 마무리한다.

Formalizer: Lean 목표 만들기

have hsum :
    a + b = 2 * (u + v) := by
  -- 이 등식의 증명이 필요

필요한 변수와 가정을 유지하며 중간 등식의 타입을 명시합니다.

Prover: 실제 증명 채우기

have hsum :
    a + b = 2 * (u + v) := by
  rw [hu, hv]
  ring
exact ⟨u + v, hsum⟩

rw는 두 가정을 대입하고, ring은 남은 항등식을 증명합니다.

exact ⟨u + v, hsum⟩는 선택한 정수와 등식의 증명을 함께 제출합니다.

분해에서 잘못된 중간 주장을 만들면, 이후 단계가 정확해도 전체 증명을 완성할 수 없습니다.

ToMap [R9]의 세 역할을 설명하기 위해 만든 교육용 예시입니다. 논문의 실제 실행 기록은 아닙니다. 코드 조각은 위 문맥과 import Mathlib를 전제로 합니다.

03 · Experimental plan Warm-up 실험 제안

다음 실험: 자연어 재설계가
직접 리팩터링보다 도움이 될까요?

조건허용할 작업알고 싶은 것
A · Direct baseline원래 Lean proof → 직접 리팩터링 + compiler feedback자연어 재설계 없이 얻는 개선
B · ExplanationA + 블록별 수학 설명설명 자체가 구조 파악에 도움이 되는가?
C · RedesignB + 새로운 자연어 proof sketch → Lean증명 경로를 바꾸면 추가 개선이 생기는가?
D · RetrievalC + 버전별 lemma/전략 검색설명의 효과와 검색 효과를 분리할 수 있는가?

통제

같은 모델·버전·문제·context, 전체 LLM 및 Lean 호출 예산을 맞춥니다. 가능하면 여러 seed로 반복합니다.

쉬운 문제만 골라 평균을 내지 않고, 실패·무개선도 전체 분모에 넣습니다.

기록

진술 보존·compile 성공 → 토큰·heartbeats·호환 버전 → 공식 combined score.

별도 기록: LLM 비용·시간, 새 lemma 수, 전략 종류, 실패 단계.

발표의 결론: 원래 정리를 고정하고, 새 증명 방법을 찾고, 통과한 후보의 세 가지 성능을 측정합니다. 자연어 단계를 넣을지는 이 비교 실험으로 판단합니다.
실험 결과를 읽는 법D가 가장 좋다고 해서 자연어 단계가 원인이라고 결론 내리면 안 됩니다. 여력이 있으면 A+retrieval도 추가해 검색만의 효과를 확인합니다. 후보 생성 비용이 다른 실험은 matched budget과 무제한 성능을 각각 보고합니다. Warm-up은 개발용이고 공개 문제 과적합이 본 benchmark 성능으로 이어진다고 가정하지 않습니다.
