00 · Starting from zero

증명을 컴퓨터가 검사한다는 것

친구가 “이 계산은 맞아”라고 말하면, 우리는 풀이를 읽고 납득합니다. Lean에서는 무엇을 주장하는지, 어떤 근거로 결론에 도달하는지를 정해진 언어로 적습니다. 컴퓨터는 그 증거가 주장을 뒷받침하는지 규칙에 따라 확인합니다.

명제 · STATEMENT

무엇을 보일 것인가?

“a가 b와 같고, b가 c와 같다면, a는 c와 같다.”

증명 · PROOF

왜 그런가?

“같다는 관계는 이어 붙일 수 있다. 두 근거를 연결하면 결론을 얻는다.”

Lean은 작성된 명제에 대한 증거를 검사합니다. 우리가 머릿속에 생각한 문제를 자동으로 알아내는 것은 아닙니다. 문제를 정확하게 옮기는 일도 필요합니다.

형식화, 증명 찾기, 리팩터링은 다른 단계입니다

A · AUTOFORMALIZATION

형식화

사람 말로 쓴 문제를 Lean 언어로 옮깁니다.

비유: 요리 설명을 정확한 레시피로 옮기기.

B · THEOREM PROVING

증명 찾기

주어진 Lean 명제를 만족하는 증거를 만듭니다.

비유: 레시피가 목표한 요리를 만드는지 보이기.

C · PROOF REFACTORING

증명 리팩터링

기존 증명을 정리해 같은 명제의 더 나은 증명을 만듭니다.

비유: 같은 요리가 나오도록 중복된 절차를 정리하기.

리팩터링: 결론은 유지하고 설명을 개선하기

정리하기 전
1. a = b라는 근거를 꺼낸다.2. 그 근거를 새 이름으로 복사한다.3. b = c라는 근거를 꺼낸다.4. 이것도 새 이름으로 복사한다.5. 복사한 근거들을 연결한다.
정리한 뒤
a = b와 b = c를 바로 연결한다.
따라서 a = c.

이 예시는 중복 제거를 설명하기 위한 풀이입니다. 논문에서 발췌한 코드가 아닙니다.

더 좋은 증명이란 짧기만 한 증명이 아닙니다. Lean이 처리하는 계산량, 읽기 쉬움, 다른 버전에서도 쓸 수 있는지도 고려합니다. 짧은 자동화 명령 하나가 내부에서 많은 탐색을 할 수도 있습니다.

① 실제 데이터 · 자연어 입력을 한국어로 요약

실수 전체의 르베그 측도는 무한대다

여기서 측도는 길이를 일반화한 개념입니다. 구간 [0, 3]의 측도는 3이고, 실수 전체의 측도는 무한대입니다.

정리
실수 전체 ℝ의 르베그 측도가 무한대임을 증명하라.

자연어 증명
임의의 r ≥ 0을 잡는다. 구간 [0, r]의 측도는 r이다. 이 구간은 실수 전체에 포함되므로, 실수 전체의 측도는 r 이상이다. 모든 유한한 r ≥ 0에 대해 이 관계가 성립하므로 실수 전체의 측도는 무한대다.
r = μ([0, r]) ≤ μ(ℝ)   →   μ(ℝ) = ∞

데이터 필드: nl_problem은 정리, nl_proof는 자연어 증명, formal은 Lean 정리·증명입니다. nl_explanation은 Lean 표현의 해설입니다. 원본 Lean 코드는 정답 쪽 자료이며, 자연어에서 Lean 후보를 생성하는 과제와 구분합니다.

② 형식화 · 어떤 타입과 근거를 선택해야 할까?

목표는 volume (Set.univ : Set ℝ) = ∞입니다. 집합의 원소는 실수 ℝ이고, 측도의 값은 ∞를 포함하는 비음수 확장실수 ℝ≥0∞입니다. 자연어의 “무한대”를 쓰려면 값의 타입도 올바르게 선택해야 합니다.

-- 원본의 증명 구조를 풀어 쓴 설명용 코드
-- Mathlib import와 이름 공간 설정이 있는 환경을 전제
example : MeasureTheory.volume (Set.univ : Set ℝ) = ∞ := by
  refine ENNReal.eq_top_of_forall_nnreal_le ?_
  intro r
  have interval_length :
      MeasureTheory.volume (Set.Icc (0 : ℝ) (r : ℝ)) =
        (r : ℝ≥0∞) := by simp
  rw [← interval_length]
  exact MeasureTheory.measure_mono (Set.subset_univ _)
Lean의 선택수학적 역할
eq_top_of_forall_nnreal_le무한대를 직접 계산하는 대신, 모든 유한한 비음수 값 r 이상임을 보인다.
intro r임의의 비음수 실수 r을 잡는다. 이후 ℝ과 ℝ≥0∞로 변환해 사용한다.
구간 측도 계산과 rw목표 r ≤ μ(ℝ)을 μ([0, r]) ≤ μ(ℝ)로 바꾼다.
measure_mono와 집합 포함 근거[0, r] ⊆ ℝ로부터 원하는 부등식을 얻어 증명을 끝낸다.

코드는 공개 예시의 구조를 읽기 쉽게 재작성했습니다. 원본은 calc로 등식과 부등식을 연결합니다. 여기서는 원본 Mathlib 버전에서의 실행을 재현한 결과로 제시하지 않습니다.

③ 설명용 실패 후보 · 실제 모델 출력이나 컴파일 로그 아님

모델이 부등식의 방향을 반대로 옮겼다면?

필요한 관계
μ([0, r]) ≤ μ(ℝ)
작은 집합의 측도 ≤ 큰 집합의 측도
잘못 작성한 관계
μ(ℝ) ≤ μ([0, r])
포함 관계로 얻는 결론과 방향이 반대

모델이 오른쪽 부등식을 중간 목표로 작성한 뒤, measure_mono에 [0, r] ⊆ ℝ라는 근거를 넣었다고 가정합시다. 이 명령은 왼쪽 부등식의 증거를 만듭니다. 단조성으로 얻은 증거의 방향은 올바르지만, 모델이 작성한 중간 목표의 방향이 잘못됐기 때문에 해당 단계에서 실패합니다.

원래 증명에 필요한 올바른 목표: μ([0, r]) ≤ μ(ℝ)모델이 잘못 작성한 중간 목표: μ(ℝ) ≤ μ([0, r])단조성으로 얻은 증거의 타입: μ([0, r]) ≤ μ(ℝ)

Lean은 모델이 코드에 적은 중간 목표와 제출한 증거의 타입을 비교합니다. 이 둘이 반대 방향이라 타입 검사가 실패합니다. 여기서 잘못된 것은 단조성의 결론이 아니라 모델이 설정한 중간 목표입니다.

두 부등식 모두 Lean에서 명제로 표현할 수 있습니다. 문장을 적을 수 있다는 사실과 그 문장을 증명했다는 사실은 다릅니다. 증명을 함께 검사해야 이 불일치가 드러납니다.

④ 컴파일 피드백 → 학습 라벨 · 단계를 단순화한 재구성

위 후보의 첫 오류가 3단계에서 발견됐다고 가정하면, 동일한 실패 결과도 OSV와 PSV는 다르게 학습합니다.

생성 과정OSVPSV
1. 무한대 판정 보조정리 적용0 · 최종 실패1 · 첫 오류 이전
2. 구간 측도 계산0 · 최종 실패1 · 첫 오류 이전
3. 반대 방향 부등식에 단조성 적용0 · 최종 실패0 · 첫 오류
4. 이후의 결론 단계0 · 최종 실패0 · 오류 이후

PSV는 “전체가 실패했다”에 더해 실패하기 전까지의 prefix도 학습 자료로 얻습니다. 자연어 문제 q와 t단계까지 생성한 Lean 코드를 보고 그 단계의 맞음 확률을 예측하도록 학습합니다.

1과 0은 컴파일 피드백으로 만든 대리 라벨입니다. 1은 자연어와의 의미 일치를 보장하지 않으며, 오류 이후의 0도 각 문장이 독립적으로 틀렸음을 확인했다는 뜻은 아닙니다.

⑤ 핵심 방법: 번역기와 평가자를 함께 개선한다

생성형식화 모델Lean 후보 만들기
→
검사Lean 컴파일러첫 오류 위치 얻기
→
학습PSV과정 라벨로 훈련
→
개선후보 선별형식화 모델 재학습

PSV가 좋은 후보를 선별해 형식화 모델의 추가 학습에 활용하고, 새 후보와 컴파일 피드백으로 평가자도 개선합니다. 목표는 명제 형식화이며, 증명 단계는 번역을 평가하는 문맥과 피드백을 얻기 위해 이용합니다.

이 예시에서는 구간 측도와 단조성을 올바르게 연결한 후보가 유망한 학습 자료가 됩니다. 이 과정은 실패한 코드 한 줄을 그 자리에서 자동 수정하는 절차와는 다릅니다. 후보 선별 → 생성 모델 미세조정 → 새 출력 컴파일 → PSV 추가 학습으로 두 모델을 개선하는 학습 루프입니다.

Lean과 PSV는 같은 검사자인가요?

Lean은 형식 규칙에 따라 실제 후보를 검사합니다. PSV는 Lean 피드백으로 학습한 예측 모델입니다. 좋은 후보를 고르는 데 도움을 주지만, 최종 Lean 검증을 대신하지는 않습니다.

컴파일 성공은 자연어 번역의 정확성까지 보장할까?

원래 입력이 “μ(ℝ) = ∞”인데 모델이 0 = 0을 생성하고 증명해도 Lean 검사는 통과할 수 있습니다. 증명까지 붙이면 검사 신호가 강해지지만, 원래 문제와 의미가 같은지는 별도로 확인해야 합니다.

논문은 과정 정보를 이용한 학습의 이점을 보고합니다. 여기서 기억할 것은 최종 성공 여부보다 오류 위치가 더 풍부한 학습 자료라는 아이디어입니다.

리팩터링에 연결 · 우리의 응용 아이디어

수정한 증명이 실패했을 때 “실패”만 남기지 않고 첫 오류와 남은 목표를 기록하면 다음 수정에 도움이 됩니다. 다만 이 추론 중 수정 아이디어와 논문의 PSV 학습 방법은 구분해야 합니다.

ProofBridge: Auto-Formalization of Natural Language Proofs in Lean via Joint Embeddings
Prithwish Jana 외 · 2025 제출, 2026 수정 · arXiv v3

비슷한 풀이를 검색해 참고하고,
정리와 증명을 함께 Lean으로 옮기자.

ProofBridge는 자연어의 정리와 증명 전체를 Lean으로 번역합니다. 사람의 설명과 Lean 정리·증명 쌍을 같은 벡터 공간에 배치하는 공동 임베딩으로 관련 예제를 검색합니다.

공동 임베딩 · 같은 아이디어 지도에 두기
사람 말

위 짝은 개념 설명용입니다. 실제 검색 결과나 임베딩 측정값이 아닙니다. 임베딩은 자료를 숫자 목록으로 표현해 가까운 자료를 찾는 방법입니다.

핵심 방법: 검색 → 번역 → 검사 → 수정

입력사람의 정리·증명무엇을 어떻게 보였나?
→

자연어와 Lean의 대응 쌍을 가깝게 학습하고, Lean 쪽에는 증명 상태의 변화 정보도 이용합니다. 검색 예제는 번역 모델의 학습과 생성에 활용하며, 이후 검사 피드백으로 반복 수정합니다.

검사는 두 질문으로 나눈다

TC · TYPE CORRECTNESS

작성한 명제를 증명했나?

정리와 증명이 Lean의 타입 검사를 통과하는지 확인합니다.

SC · SEMANTIC CORRECTNESS

참조 명제와 같은 뜻인가?

생성한 Lean 명제와 참조 Lean 명제 사이의 쌍방향 함의를 증명하는 평가를 사용합니다.

쌍방향 함의란 무엇인가요?

“A라면 B”와 “B라면 A”를 모두 보이는 것입니다. 두 표현의 논리적 동치를 확인합니다. 다만 이것을 자연어의 모든 뉘앙스까지 자동으로 확인한 결과로 해석해서는 안 됩니다.

이 평가는 참조 Lean 명제가 원래 자연어를 충실하게 표현한다는 가정에 의존합니다. 논문은 검색·번역의 개선을 보고하며, 코드 통과와 의미 충실도를 따로 평가한다는 관점이 중요합니다.

리팩터링에 연결 · 우리의 응용 아이디어

“귀납 대상 바꾸기”처럼 도움이 될 전략과 예제를 먼저 찾고 증명을 수정할 수 있습니다. ProofBridge의 원래 과제는 번역이며, 리팩터링 전략 검색은 우리가 확장해 볼 방향입니다.

출처: 원문 v3 · §4의 공동 임베딩과 시스템, §5의 평가, Appendix A.4의 semantic equivalence. 지도와 예시는 설명용 재구성입니다.

miniF2F-Lean Revisited: Reviewing Limitations and Charting a Path Forward
Azim Ospanov, Farzan Farnia, Roozbeh Yousefzadeh · 2025 · arXiv v1

번역과 증명을 따로 채점하는 데서 나아가,
원래 문제를 해결했는지 확인하자.

문제: 문제집의 번역에도 오류가 있을 수 있다

miniF2F는 수학 문제와 형식 명제를 연결한 벤치마크입니다. 이 논문은 자연어와 Lean 명제의 불일치를 분석하고, 수정 버전을 제시하며, 형식화와 증명을 연결한 전체 과정을 평가합니다.

원래 숙제 · 설명용 예시

“모든 상자에 사과가 있다”

상자를 하나만 확인해서는 끝나지 않습니다. 각 상자에 대해 보여야 합니다.

잘못 옮긴 숙제 · 설명용 예시

“어떤 상자에 사과가 있다”

사과가 든 상자 하나를 찾으면 끝납니다. 더 쉬운 다른 문제입니다.

위 예시는 양화사 변경의 영향을 보여주기 위한 비유입니다. miniF2F의 특정 오류 사례를 인용한 것이 아닙니다.

Lean 검증 통과만 세는 평가와, 원래 문제에 충실한 풀이만 인정하는 평가를 구분합니다. 형식화 결과에는 Lean 전문가의 의미 검토도 사용합니다.

성공률을 읽을 때 함께 물어야 할 것

  1. 1
    어느 단계의 성공률인가?
    번역만 성공했는지, 증명만 성공했는지, 전체가 성공했는지.
  2. 2
    성공을 누가 판단했는가?
    Lean 검사인지, AI의 의미 평가인지, 전문가 검토인지.
  3. 3
    시도를 몇 번 허용했는가?
    한 번의 결과와 여러 후보 중 성공 하나를 찾는 평가는 조건이 다릅니다.

이 세 질문은 논문을 읽기 위한 체크포인트입니다. 숫자가 높다는 이유만으로 서로 다른 평가를 바로 비교할 수는 없습니다.

논문은 명제 불일치와 평가자에 따른 차이를 보고합니다. 기억할 결론은 개별 도구의 높은 성능이 원래 문제에 대한 전체 성공률을 보장하지 않는다는 것입니다.

리팩터링에 연결 · 우리의 응용 아이디어

리팩터링은 주어진 Lean 명제를 유지해야 합니다. 더 쉬운 명제로 바꾸고 짧게 증명하면 개선이 아닙니다. 먼저 명제와 환경 보존을 확인하고, 그 뒤 길이와 처리 비용을 비교해야 합니다.

출처: 원문 v1 · §2의 벤치마크 분석, §3의 전체 파이프라인, §4의 번역 평가. 상자·사과 예시는 설명을 위해 만들었습니다.

우리가 만들 수 있는 최소 개선 루프
  1. 기존 명제와 증명을 읽는다. 무엇을 증명하고 있는지 한 문장으로 설명한다.
  2. 전략과 예제를 찾는다. 중복 제거, 귀납 대상 변경 같은 후보를 만든다.
  3. Lean으로 확인한다. 실패하면 첫 오류와 남은 목표를 보고 고친다.
  4. 개선을 측정한다. 명제·공리 의존성을 확인하고 길이, 처리 비용, 지정 버전 호환성을 비교한다.

우리 warm-up 2번도 이렇게 읽을 수 있습니다

좋은 리팩터링은 지워도 되는 이유를 설명할 수 있는 수정입니다. 그리고 짧아졌다는 관찰과 계산 비용도 줄었다는 측정은 따로 확인합니다.

05 · Check your understanding

이 세 질문에 답할 수 있다면

답을 보기 전에 한 문장으로 설명해 보세요.

1. Process-Driven은 왜 첫 오류 위치를 사용하나요?

최종 실패 하나보다 어느 단계부터 문제가 생겼는지 더 많은 정보를 주기 때문입니다. 논문은 이 라벨로 PSV를 학습하고 형식화 모델 개선에 활용합니다.

2. ProofBridge의 공동 임베딩은 무엇을 연결하나요?

자연어 정리·증명과 Lean 정리·증명 쌍을 같은 공간에서 연결해 관련 예제를 찾도록 합니다. 찾은 예제는 번역을 돕고, 최종 후보는 따로 검사합니다.

3. Lean이 통과시킨 증명도 원래 문제의 정답이 아닐 수 있나요?

그럴 수 있습니다. Lean은 작성된 명제를 검사합니다. 명제를 잘못 번역하거나 더 쉽게 바꿨다면, 통과해도 원래 문제를 풀었다고 할 수 없습니다.
