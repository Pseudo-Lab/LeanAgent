종료 코드, 빈 goals, 정보 부재의 차이

세 값은 서로 다른 상태를 나타낸다. 어느 하나만으로 증명 완성을 판정하지 않는다.

01 · PROCESS

종료 코드가 0이다

returncode: 0
warning: declaration uses 'sorry'

CLI가 오류 없이 종료했다는 뜻이지, 요구한 증명을 완성했다는 뜻은 아니다.

02 · GOALS

goals가 비었다

"goals": [],
"proofStatus":
  "Incomplete: contains sorry"

목표를 sorry로 닫은 경우에도 빈 목록이 반환됐다.

03 · FIELD ABSENCE

goals 필드가 없다

{
  "message": "Lean error: …"
}

실패한 tactic 응답에는 goals가 없었다. 이를 빈 목록으로 바꾸면 안 된다.

관측된 값해석허용하지 않을 판정
goals = null목표 정보를 받지 못함 / 해당 backend가 제공하지 않음목표가 0개라고 간주
goals = []backend가 실제 빈 목록을 반환이 값만으로 최종 성공 선언
goals = […]남은 목표 또는 수집된 상태 정보가 있음진단 문맥과 완성 판정을 혼동

REPL 프로세스도 내부 요청에 Lean 오류가 있었지만 종료 코드는 0이었다. 프로세스 상태와 요청별 진단을 분리해야 한다. JSON의 “…”는 메시지 발췌 표시다.

참고문헌R03R12

완성된 proof state와 실제 선언도 다르다

REPL 내부에서 목표를 끝내는 것과 원래 환경의 정리를 수정하는 것은 별개였다.

REPL 내부 상태 완성
"proofStatus": "Completed",
"goals": []

#print axioms and_swap
-- original env: [sorryAx]

완성한 proof state가 원래 environment의 선언을 자동으로 교체하지 않았다.

전체 proof를 다시 조립한 뒤
수정 proof를 포함한 전체 선언 재입력

#print axioms and_swap
-- does not depend on any axioms

실제로 반영한 전체 선언을 재검증한 뒤에야 원래 정리의 완성을 확인했다.

여기서는 모델이
수정 방법을 찾지 않았다

04프로젝트용 최소 검증·수리 설계

승인된 증명 본문만 바꾸고 전체 파일을 검사한다. 모델의 후보 생성과 실행기의 최종 수락을 분리한다.

읽는 범위 · 수정 범위 · 검증 대상을 분리

proof body는 정리의 := 오른쪽에 오는 증명 항이다. 이번 모델은 by로 시작하는 본문 전체를 반환한다.

READ · 모델에게 보여주는 것

문제와 필요한 문맥

정리문, 오류 파일, 관련 정의·문맥, 실제 Lean 진단, 확보한 goal과 가정.

WRITE · 모델이 바꾸는 것

승인된 선언의 proof body

응답은 diagnosis와 proof_body.
import·명제·가정·정의는 고정한다.

VERIFY · 실행기가 검사하는 것

전체 파일과 최종 대상

수정 body를 고정 문맥에 넣고, 정확한 최종 정리의 검사와 공리를 확인한다.

사례수정 대상으로 지정할 선언최종 검증 대상으로 지정할 정리
P7Typing.progress의 bodyTyping.progress
P12tensor_success_split의 bodyinterleaved_affine_gaps_imply_tensor_gaps
“파일 전체를 읽는다”와 “파일 전체를 수정한다”는 다르다.
P12를 수용하려면 수정할 선언과 최종 검증할 정리를 별도 필드로 둔다.

실제 모델 연결은 P7의 단일 선언에만 구현했다. P12의 승인된 보조정리 수정 인터페이스는 이 사례에서 도출한 프로젝트 확장 제안이다.

파일 전체를 보여주는 것과 전체를 수정하게 하는 것은 다르다

모델은 import와 정의, 정리문, 기존 증명, 오류를 읽을 수 있다. 그러나 반환할 수 있는 내용은 승인된 선언의 proof_body로 제한한다. 실행기는 그 본문을 원래 파일 문맥에 넣어 전체 파일을 검사한다.

P12에서는 수정할 선언과 검증할 정리가 다르다

tensor_success_split은 주 정리 앞의 별도 보조정리다. 이 보조정리의 본문을 수정하더라도 최종 수락 대상은 이를 사용하는 interleaved_affine_gaps_imply_tensor_gaps다. 정리문 자체의 결함 가능성은 proof 수리와 구분해 별도 검토 대상으로 보고한다.

모델은 수정 후보를 제안하고 실행기가 검사

모델 응답

전체 본문을 JSON으로 반환

- rcases ihLeft rfl wholeTyped with ...
+ rcases ihLeft rfl leftTyped with ...

모델 진단 요지: 전체 application의 typing이 아니라, t₁의 typing인 leftTyped를 전달해야 한다.

위 표시는 코드·입력의 발췌다. 실제 변경에는 끝의 빈 줄 제거도 포함된다. 전체 JSON과 diff를 보존했다.

다음 비교 제안: 같은 오류 코드·모델·예산에서
A = 진단 메시지 / B = 진단 + 실제 goal·가정. 여러 오류 사례와 반복 실행으로 비교한다.

이번에는 B에 해당하는 입력으로 한 사례를 실행했을 뿐, A/B 비교를 수행하지 않았다. 토큰 사용량은 기록했지만 금액은 제공되지 않아 추가 비용 0원을 주장하지 않는다.
