02 · 구현

한 정리를 고정하고 proof body만 수정한다

고정 문제 등록, 입력 검사, 오류 분류, 수정, 최종 수락을 controller가 관리한다.

  1. TaskSpec명제·문맥·환경 고정
  2. LeanRunner현재 후보 검증·진단
  3. RepairPolicyproof body 수정
  4. FinalVerifier새 프로세스 전체 검사

반복하는 구간

proof 오류는 실제 진단과 이력을 다음 수정에 전달한다. 최종 검사에서 증명 오류가 나면 남은 예산 안에서 다시 수리한다.

즉시 중단하는 경우

명제·고정 문맥 불일치, 환경 실패와 예산 소진은 종료 이유를 남긴다. 새 후보는 별도 파일로 보관한다.

하나의 Python controller와 adapter로 책임을 연결했다. 독립된 여러 에이전트의 실행을 뜻하지 않는다.

발표자 노트

구현의 기본 수리 한도는 3회입니다. 후속 V-B 실험은 별도 harness에서 최대 4회 호출합니다. imports·명제·가정·정의를 고정하고 전체 proof body만 교체합니다. 같은 후보는 캐시하되 자원·프로세스 실패는 확정적인 proof 판정으로 저장하지 않습니다.

07 · 해석의 범위

이번 결과의 적용 범위

15문제 개발 표본에서 관측한 로컬 비교 결과다.

확인한 범위

  • 고정 fixture에서 엄격 수락 조건의 필요성
  • 오류 유형별 피드백 비교와 중단 이유
  • fallback을 포함한 정상 proof 개선
  • 같은 후보군의 선택 정책 차이

남은 확인

  • 별도 평가 표본에서의 일반화
  • 피드백 구성과 프롬프트 비용의 영향 분리
  • 독립 의미 Comparator와 적대적 코드 sandbox
  • 공식 worker와 계측·규칙 동등성

같은 호스트에서 실행이 겹쳤다. wall time 지연과 timeout을 격리된 성능이나 공급자 오류율로 해석하지 않는다.

발표자 노트

문제별 환경 수는 1~4개이며 단일 버전 통과를 여러 버전 호환성으로 부르지 않습니다. 고정 문맥·구문 guard는 신뢰 경계를 좁히지만 일반적인 의미 비교나 OS sandbox를 대신하지 않습니다. 15문제의 기술통계를 외부 문제 집합의 성능으로 일반화하지 않습니다.
