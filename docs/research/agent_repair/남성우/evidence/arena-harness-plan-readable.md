# Arena 검증·수리 harness: 함께 만들 전체 계획

2026-10-13. Python 라이브러리로 시작하고 Lean을 연결하는 방향은 사용자와 합의했다. 구현·설치·유료 실험 전의 계획이다.

트랙 확정: closed-source. 공식 예산은 문제별 API $3이며, 확인한 공개 규칙에는 로컬 Lean 검증 횟수·총 CPU 시간·하드웨어 상한이 없다. 로컬 검증을 충분히 반복하는 방향으로 설계한다. 시간 기록은 개발 진단용 선택 사항이고, 개별 실행 timeout은 멈춘 프로세스 회수를 위한 설정이다. 전체 로컬 탐색 budget은 대회 제한으로 두지 않는다.

**목표: Lean으로 확인할 수 있는 일은 먼저 확인하고, 모델에는 수정이 필요한 부분만 요청한다.**

## 전체 흐름

```text
원본 문제·환경 고정 → 전략 담당이 후보 전달
  → 규칙 검사 → 빠른 Lean 검증
       ├─ 통과 → 원래 파일에서 최종 검증 → 평가 담당에 전달
       └─ 실패 → 오류·goal·가설 정리 → 제한된 로컬 수리
                    ├─ 해결 → 전체 후보 재검증
                    └─ 미해결 → 모델 국소 수리 → 다시 검증
```

실패하면 원본 또는 지금까지 검증된 최선의 증명을 보존한다.

## 합의한 후보 선택과 fallback

검증된 후보를 token 감소율·heartbeat 감소율·robustness(지정 버전에서 같은 proof가 통과하는 비율)의 combined score로 비교한다. 원본도 같은 환경과 측정 방식으로 평가한다. 원본보다 점수가 **엄격히 높은** 후보 중 최고점을 반환한다. 더 나은 후보가 없거나 동점이면 원본 proof body를 반환한다. 이때 원본 자체의 유효성 확인은 선행 조건이다.

‘최고점’은 탐색하고 평가한 후보 집합 내 최고점이다. 전역 최적 증명을 찾았다는 뜻은 아니다. 한 지표가 나빠져도 combined score가 개선되면 선택할 수 있다. 점수가 좋아 보여도 규칙·기본 correctness를 위반한 후보는 제외한다. robustness 측정 누락은 통과로 간주하지 않고 동일 body로 각 환경을 실제 검사한다. 환경 문제로 검사하지 못한 값은 실패/0과 구분하고 결과가 해결되기 전 선택을 보류한다.

공식 tokenizer·heartbeat 계측과의 일치가 확인되지 않은 동안은 local estimate로 표시한다. 비교할 metric이 누락된 후보는 개선이 확인된 후보로 채택하지 않는다. 후보 탐색의 총 Lean 시간과 최종 proof의 heartbeat는 구분한다.

검증용 데이터는 [데이터 설계](arena-pipeline-validation-data.md)의 작은 실제 Lean fixture, 오류 주입, 점수 선택 mock, 버전 검증 데이터로 준비한다.

## 팀의 세 역할

| 담당 | 일 | 출력 |
|---|---|---|
| 구조·전략 | 리팩터링 방향과 후보 생성 | proof body, 전략 의도, 수정 범위 |
| **검증·수리** | 검사, 오류 정리, 로컬/모델 수리, 재검증 | 검사 보고서, 새 후보 또는 실패 사유 |
| 실행관리·평가·재현 | 환경 준비, 예산, 실행 기록, 점수·제출 | runner, 비용 ledger, 평가 결과 |

검증·수리 모듈은 Python 함수로 호출한다. 모델이나 상위 SDK가 바뀌어도 재사용한다.

## 1단계: API 없이 후보 검사

입력은 문제 ID, 후보 proof body, 고정 실행 환경이다. 출력은 다음 내용을 담은 보고서다.

- 원래 명제·문맥 보존 여부.
- 제출 규칙 검사 결과.
- 실제 Lean 컴파일 결과와 오류 위치.
- 오류 종류, 가능한 경우 실제 goal·가설.
- 미완성 증명 여부, 대상 정리의 공리 의존성.
- 후보 hash, 실행 환경, 시간, 로그 위치.

컴파일 성공만으로 완성이라고 판정하지 않는다. sorry가 남아도 종료 코드가 0일 수 있다. 다른 정리의 기존 경고와 대상 정리의 sorryAx 의존성은 구분한다.

원본 theorem을 import해서 그것을 그대로 참조하는 검증을 피하도록, 실제 선언의 몸체를 교체한 환경에서 검사한다. 목표 타입과 imports를 모델이 편집하지 못하게 한다.

첫 시험에는 1·2번 정상 후보와 unknown identifier, 남은 goal, sorry, statement 변조, 금지 패턴, timeout, 환경 실패를 주입한 후보를 쓴다.

## 2단계: Lean 연결과 빠른 경로

최종 판정은 원래 파일에서 표준 Lean/Lake로 한다. 반복 수리 중에는 대상 직전 문맥을 재사용하는 빠른 경로를 시험한다.

LeanInteract 기반 adapter를 유지하면서 **LeanProbe 재사용 실험을 추가**한다. 먼저 지정 버전·same-file 문맥에서 CLI와 통과/실패 결과가 일치하는지 확인한다. 지원되지 않는 환경은 CLI로 계속 처리한다.

우리 cache key에는 theorem, 앞부분 문맥, dependency revision, toolchain, 검사 설정을 포함한다. 바뀌면 재준비한다. 실패 후보의 환경을 다음 후보에 물려주지 않는다. 자기 원본 theorem 참조, 실패 상태 오염, cache 무효화도 시험한다.

빠른 검사 지연과 제출 proof의 heartbeat는 별도 지표다. cache로 빨라졌다고 공식 점수가 좋아졌다고 보고하지 않는다.

## 3단계: 제한된 로컬 수리

현재 환경에서 사용 가능한 tactic만 작은 목록으로 시험한다. 예: assumption, rfl, simp. aesop, omega, ring 등은 이미 사용할 수 있는 환경에서만 추가한다.

| 결과 | 다음 행동 |
|---|---|
| 실행 오류 | 후보 버림 |
| 상태 변화 없음 | 같은 시도 반복하지 않음 |
| 목표 변화, 아직 미완성 | 제한된 후속 탐색 후보로 보관 |
| 해당 상태의 목표 해결 | 전체 proof 조립 후 실제 파일 재검증 |

목표 개수가 줄었다고 더 좋은 증명이라고 단정하지 않는다. 목표들은 의존성을 공유할 수 있다. 탐색 깊이·시간 한도는 로컬 실행 효율에 맞춰 조정하는 구현 정책이며 대회 상한이 아니다. 상태를 얻지 못하는 문법 오류는 별도 경로로 처리한다.

## 4단계: 모델 국소 수리

추가 검토: valid proof를 얻어도 최종 선택으로 바로 끝내지 않는다. simp?/aesop? 등으로 명시적 proof 추출을 시험하고 raw 후보와 함께 채점한다. 비용이 크거나 개선 여지가 있으면 모델에 실패 수리 대신 **성공한 proof의 점수 최적화**를 요청한다. 수리·최적화 API 비용은 같은 $3에 합산한다. 기존 best를 보존하며 자세한 정책은 [자동화 수리 후 최적화](automation-repair-and-optimization.md)에 정리했다.

모델에는 첫 유의미한 오류, 관련 코드, goal·가설, 전략 의도, 허용 patch 범위, 실패 이력, 남은 예산만 보낸다. 수정안 또는 포기를 받는다. 환경 오류는 모델에 보내지 않는다.

수리 최대 2회 같은 초기 정책을 두고 실제 비용에 맞춰 조정한다. 수정안을 받으면 처음 검사부터 다시 한다. 모델의 성공 설명은 인증서가 아니다.

## 첫 단계부터 넣을 지속 상태

문제마다 후보, 진단, 실패한 patch, retry, best valid, API usage, 최신 검증 hash를 대화 밖의 파일/DB에 기록한다. 재개할 때 이 기록을 사용한다.

한 문제 안에서는 처음에 하나의 active 후보만 처리한다. 문제 사이 병렬화는 실행 담당이 할 수 있다. 상태 전이는 Python이 관리한다.

```text
waiting → checking → local_repair/model_repair → final_check
                                         → accepted/failed/budget_exhausted
```

환경 실패도 별도 상태로 기록한다. SDK hook은 이 상태 전이에 검증·기록을 연결한다. 최신 후보 hash의 최종 인증서가 없으면 accepted가 될 수 없다. stop hook은 무한 재시도를 만들지 않는다.

## Lean Copilot을 어디에 둘까?

모델이 여러 tactic을 제안하고 Lean이 각각 확인하는 인터페이스를 설계한다. **Lean Copilot package 자체는 기본 검증기 이후의 선택적 backend**다.

탐색 환경에서 plugin을 사용하더라도 얻은 일반 tactic proof는 원래 Arena 환경에서 검증한다. 추가 dependency/import나 Copilot 전용 tactic에 의존하면 현재 후보로 채택하지 않는다. 호환 버전·native 의존성·premise snapshot은 도입 실험에서 확인한다.

로컬 모델 추론은 API 비용이 없더라도 하드웨어와 시간을 기록한다. 외부 API 추론은 같은 문제 비용에 합산한다. local/open 모델과 closed API의 혼합은 트랙 해석을 확인한 뒤 선택한다.

## 구현 순서와 완료 기준

| 순서 | 결과물 | 완료 기준 |
|---|---|---|
| 1 | Python 검증 core | 정상/오류 후보 정확히 분류, API 없이 실행 |
| 2 | Lean 연결·빠른 경로 시험 | CLI 판정 일치, 실패 환경 격리·cache 무효화 |
| 3 | 로컬 수리 | 상태 복구·일반 proof 조립·파일 재검증 |
| 4 | 모델 수리 하나 | 범위·retry·비용 제한, best valid 보존 |
| 5 | 평가·재현 연결 | 동일 proof의 버전 결과, 명시된 계측, 제출 export |
| 6 | 비교 실험 | 빠른 검사·로컬 수리·모델 제안의 효과 분리 |

실험은 동일 초기 후보·모델·API cap·local compute 한도로 비교한다. 성공률, API 지출, Lean 시간, 최종 token/heartbeat/compatibility를 따로 보고한다. 최종 proof 선택은 평가 담당과 한다.

## 이번에 바꾼 부분

- Python 시작과 Lean 연결은 합의 사항으로 확정.
- LeanProbe 재사용 시험 추가.
- 빠른 검사와 최종 검증, cache 무효화를 명시.
- 문제별 지속 상태를 첫 core에 포함.
- 로컬 tactic 결과를 오류/무변화/미완성 변화/해결로 세분화.
- Lean Copilot의 모델 제안 기능은 선택적 확장으로 추가.
