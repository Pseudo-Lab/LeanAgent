# 검증 피드백으로 Lean 증명을 수리하고 선택하기

남성우 · 2026-10-25 발표 · 근거: `docs/week2-namsungwoo`의 2026-10-22 커밋. 문헌·설계는 당시 조사 기록이며 현재 도구 지원 범위를 새로 검증한 문서는 아닙니다.

## 연구 질문과 파이프라인

실패한 증명을 무조건 모델에 다시 보내지 않고, Lean으로 검사 가능한 부분을 먼저 처리할 수 있는가? 원문·환경 고정 → 후보 계약 검사 → 전체 파일 컴파일·공리 검사 → 로컬 수리 → 재검증 → 필요한 경우 모델 escalation → 점수 비교·fallback 순서로 설계했습니다. 성공한 후보도 길이·heartbeat·지정 버전 호환성을 함께 비교합니다.

## 실행으로 확인한 내용

1. **오류 줄과 원인은 다를 수 있습니다.** R02의 잘못된 intro, R05의 잘못된 left 선택, R06b의 앞선 가설 삭제는 마지막 오류 줄만 치환해서 해결되지 않았습니다.
2. **국소 성공은 전체 성공이 아닙니다.** R08에서 simp?/exact? 제안은 현재 목표를 닫았지만 뒤쪽 죽은 tactic 때문에 전체 replay가 실패했습니다.
3. **짧은 자동화가 더 저렴하지 않을 수 있습니다.** R04의 raw aesop은 로컬 HB 68→119, 명시적 script 추출은 69였습니다. 공식 점수가 아닌 단일 환경 관찰입니다.
4. **유효한 증명에도 후처리 여지가 있습니다.** minimizer A는 Warm-up 15문제 중 P1·P2·P12를 개선했고 평균 추가 점수는 0.547점입니다. 개선량의 73.6%가 P12에 집중됐습니다.

## 선택 규칙과 한계

원본과 후보를 동일 환경에서 비교하고, 더 좋은 검증된 후보가 없으면 기존 최선·원본을 유지합니다. 환경 실패나 누락을 임의의 robustness 0점으로 치환하지 않습니다. minimizer의 악화 0건은 선택·fallback의 결과이며 모든 제안이 좋았다는 뜻이 아닙니다. 310제안 중 유효한 고유 증명은 4개였습니다.

원본 토큰 15/15는 제공값과 같지만 Putnam HB는 P13 +26.56%, P14 −10.42%, P15 +27.05% 차이가 있어 공식 worker 재현 성공으로 주장하지 않습니다. 단일 실행의 근소한 HB 차이는 반복 검증이 필요합니다.
