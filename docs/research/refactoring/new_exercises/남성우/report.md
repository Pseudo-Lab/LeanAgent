# 실험 A 리뷰

## 최종 결과

15문제, 36개 문제·버전 조합을 완료했다. 선택된 최종 증명은 36/36에서 통과했다.
평균 로컬 final score는 **35.238 → 35.785 (+0.547점)**, 개선 중앙값은 **0점**이다.
추가 개선은 P1(+2.002), P2(+0.160), P12(+6.038)의 3문제다.
실제로 A를 탐색한 14문제 중 3문제(21.4%)에서 개선했고, P8은 요청대로 제외했다.
나머지 12문제는 기존 선택/원본을 유지했다. 원본 fallback은 P7·P8이며,
최종 증명이 원본보다 좋은 문제는 13개다. 이 13개 모두가 A의 성과는 아니다.

310개 수정 제안에서 서로 다른 유효 후보는 4개(약 1.3%)였다.
최종 개선량의 **73.6%가 P12 한 문제**에서 나왔다. 따라서 “추가 모델 호출 없이
일부 불필요한 증명 단계를 찾는다”는 가설은 지지하지만, 대부분의 문제를
효율적으로 개선하는 일반 정책이라고 결론 내릴 수는 없다.
평균 점수 기여는 토큰 +0.307점, HB +0.240점, 호환성 변화 0점이다.

`simp?` 61회 중 유효 후보 1개, `exact?` 58회 중 1개, 삭제 31회 중 2개였다.
`aesop?` 44회, `assumption` 58회, `rfl` 58회는 유효 후보를 만들지 못했다.
이는 현재 구간 선택 방식에서의 결과이며 tactic 자체의 일반적 성능 순위가 아니다.
107회의 no_supported_suggestion은 모두 해당 query의 전체 검증도 실패했다.
이 가운데 20회에 Try this 텍스트가 있었지만, 이를 “추출만 개선하면 해결될 20개”로
해석할 근거는 없다. 이 실행에서는 유효하지만 대조군보다 점수가 낮은 후보는
발견되지 않았다. 그런 후보의 거절은 단위 테스트로 검사했다.

모델 API 호출은 0회다. 개발 대화와 과거 모델 후보 생성 비용을 0이라고 주장하지
않는다. 이 수치는 공식 Arena worker 제출 점수가 아니라 로컬 재계측 결과다.


## 비교의 의미

이번 실행은 이전 모델 후보 생성 실험을 다시 돌린 것이 아니다. 이전에 선택한
증명에 결정적 로컬 후처리 A를 추가했을 때의 효과를 측정한다. 대조군과 A 후보,
원본을 같은 지정 환경에서 새로 검증한다. 과거 o200k_base 점수는 이번 구문 토큰
점수와 직접 비교하지 않는다.

## 구현 검토

- 구간 위치는 Lean Syntax의 UTF-8 byte 좌표를 사용한다. 실제 의존성 그래프는 아니다.
- 후보의 proof body 밖 원문은 고정한다. audit.py는 저장된 원본/후보 전체 파일의
  prefix/suffix를 직접 비교한다. 계측 및 AST 추출용 복사본은 별도이며 제출 후보가 아니다.
- 탐색 tactic의 출력은 그대로 채택하지 않는다. 위치가 맞는 한 줄 명시적 제안을
  추출하고 전체 파일·공리·HB를 다시 확인한다. sorry 제안은 버린다.
- 기본 버전에서 유효한 모든 고유 후보를 지정된 다른 버전에서 그대로 검사한다.
  timeout/환경 오류/누락은 낮은 robustness로 점수화하지 않고 미완료로 남긴다.
- 최종 선택에 원본/기존 최선이 포함되므로 악화를 막는다. 개선을 보장하지는 않는다.
- P8은 원본만 검증하며 자기참조 허용 정책은 변경하지 않았다.

## 실제 관찰로부터의 해석

P1에서는 중간 `have assoc`를 제거해도 뒤의 `simp_all` 기반 증명이 성립했다.
이 보조사실을 명시적으로 만드는 단계가 불필요했음을 해당 문맥에서 검증한 것이다.
모든 `have`를 삭제해도 된다는 결론은 아니다.

P2에서는 `apply trih <;> assumption`을 `exact trih tr_normalized`로 바꿨다.
필요한 가정을 직접 지정한 작은 변화다. HB 차이는 작으므로 속도 개선을 일반화하지
않으며, 이 실행의 토큰·HB 결합 점수만 보고한다.

P4에서는 `inner_pos₂`와 `bump_exists`를 삭제하면 뒤의 사용처에서
`Unknown identifier` 오류가 발생했다. 전체 proof를 검사해야 하는 이유다.
전체 목표를 대상으로 한 aesop?은 해결하지 못했고, 일부 구간은 기존 maxHeartbeats
한도에 걸렸다. 자동화가 모든 큰 구간을 대체할 것이라는 가정은 맞지 않았다.

P12에서는 확률 조건을 집합 크기 부등식으로 바꾸는 `have h_R_star_card_gt_eps`
블록을 삭제해도 동일 증명이 Lean 4.31/4.30/4.29에서 모두 통과했다.
기존 선택 대비 116 토큰, 약 885.448 HB를 줄여 +6.038점을 얻었다.
수학적 주장을 약화한 것이 아니라, 최종 증명에 불필요했던 보조 결과의 구축을
제거한 것이다. 이는 여러 단계를 새 정리로 대체한 C의 성과와 구분해야 한다.
삭제한 블록 앞의 설명 주석은 남아 있으므로, 점수 개선을 완전한 가독성 개선으로
해석하지 않는다. 이 실행에서는 선택 후 proof body를 수동으로 다듬어 검증된
후보와 다른 코드를 제출하지 않았다.

대조군 P9는 원본 251 토큰보다 긴 253 토큰이지만 HB가 3,856.574에서
2,689.966으로 줄어 최종 점수 43.151을 얻었다. A는 이를 더 개선하지 못해 그대로
유지했다. 이 성과를 A의 성과로 세지는 않지만, 길이만 최적화하지 않아야 하는
실제 비교 사례다.

## 다음 정책에 반영할 후보

1. have 명령 전체와 have 내부 증명을 별도 구간 유형으로 다루기.
2. 뒤에서 이름을 쓰는 have 삭제의 우선순위를 낮추기. 문자열 사용 여부만으로
   수학적 의존성을 확정하지 않고, 보수적 휴리스틱임을 표시하기.
3. 여러 줄 제안 지원 전후를 분리 실험하기. no_supported_suggestion을 증명 실패와
   추출 실패로 구분하기.
4. 근소한 HB 차이는 반복 측정 후 결정하기.
5. 이 개발 실행의 규칙을 고정한 뒤 별도 테스트 데이터를 평가하기.

후속 정책 제안은 이번 성과를 부풀리기 위해 실행 중 탐색 정책에 추가하지 않았다.
최종 수치와 개별 증명 diff는 results.json 및 presentation.html에 기록한다.


## 제공 heartbeat와의 차이

원본 토큰은 15/15 제공값과 일치하지만, Putnam 원본 HB는 P13 +26.56%,
P14 −10.42%, P15 +27.05% 차이가 난다. 원인은 확정하지 않았다.
이를 잡음으로 무시하거나 공식 worker 재현 성공으로 표현하지 않는다.
이번 점수는 동일한 고정 환경·계측기로 원본과 후보를 새로 잰 상대 비교다.
Putnam에서는 A 전후 선택이 같아 이번 추가 개선량에는 기여하지 않았다.
`measurement-comparison.json`에서 전체 값을 확인할 수 있다.
