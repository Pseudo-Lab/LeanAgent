## 결론

**두 문제 모두 이번 세션에서 재검증한 기존 best보다 HB와 proof tokens가 줄었다.** P8은 명시적 귀납·직접 증거 구성·등식 처리 정리, P11은 긴 좌표 전개를 선행 보조정리로 대체한 결과다. 같은 변환을 두 정리에 적용한 것이 아니므로 범용 전략의 일반화 증거와는 구분한다.

| 문제 | 원본 HB / 토큰 | 시작 best HB / 토큰 | 이번 best HB / 토큰 | 시작 best 대비 HB 감소 | 시작 best 대비 토큰 감소 |
| --- | ---: | ---: | ---: | ---: | ---: |
| P8 · c003 | 1,382 / 407 | 1,320 / 412 | **380 / 382** | **71.21%** | **7.28%** |
| P11 · c002 | 45,537 / 1,906 | 38,337 / 1,379 | **21,010 / 966** | **45.20%** | **29.95%** |

원본 대비는 P8 HB **72.50%**, 토큰 **6.14%** 감소; P11 HB **53.86%**, 토큰 **49.32%** 감소다. 원본 대비 누적 개선과 이번 시작 best 대비 추가 개선을 혼용하지 않는다.

표의 원본·시작점·최종 후보는 모두 이번 세션에서 각각 3회 전체 파일 검증·공리 검사·별도 HB 계측했다. 모든 반복값이 같아 각 HB 중앙값·최솟값·최댓값은 표의 값과 같다. 과거 수치를 새 기준선 대신 사용하지 않았다. 로컬 v4.31.0 결과이며 공식 점수가 아니다.

### 왜 좋아졌나 — 결과와 원인 추정을 구분

기존 proof는 cases 분기 뒤 대상 정리의 정당한 구조적 재귀 호출로 부분항 합류를 구했다. 새 proof는 첫 번째 축약 증거에 귀납하여 부분항에 대한 귀납 가설을 직접 사용한다. 분기 내부에서는 `use/constructor/apply` 연쇄 대신 공통 항과 양쪽 축약 증거를 직접 구성한다.

발견 후 다음 대조군을 추가했다. 이는 최초 탐색 전 사전 등록된 요인 실험이 아니라, 관찰 이후 구성한 제한된 효과 확인이다.

|  | 기존 분기 구성 | 직접 증거 구성 |
| --- | ---: | ---: |
| 기존 cases·재귀 | 시작 best: 1,320 HB | c006: 773 HB |
| 명시적 귀납 | c004: 1,000 HB | c001: 429 HB |

- 귀납 변경의 관찰 효과: 기존 분기 구성에서 **320 HB 감소**, 직접 구성에서 **344 HB 감소**.
- 직접 구성의 관찰 효과: 기존 골격에서 **547 HB 감소**, 귀납 골격에서 **571 HB 감소**.
- 두 변경 결합 감소 891 HB는 단독 감소의 합 867 HB보다 **24 HB 크다**. 가산적 예측보다 24 HB 낮은 값이다.
- c001 → c003 정리는 추가로 **49 HB, 52토큰 감소**했다.

따라서 “귀납법만 바꿔서 전체 940 HB를 줄였다”는 설명은 틀리다. 귀납 골격, 직접 구성, 후속 등식 처리 모두 기여하는 관찰이다. 내부 elaborator·tactic별 profiling은 하지 않았으므로 위 차이를 특정 내부 연산의 고정 비용으로 해석하지 않는다. c005→c006은 이름 수리이며 최종 대조군은 실제 원문과 diff로 확인할 수 있다.

### 적용 조건

부분 증거에 대한 재귀가 있고, 각 분기의 결과를 구체적 생성자로 조립할 수 있는 경우 명시적 귀납 가설과 직접 구성을 검토한다. 모든 재귀 proof가 같은 폭으로 개선된다는 주장은 아니다. 추론 가능한 witness 생략도 elaboration 비용을 늘릴 수 있으므로 측정이 필요하다.

## P11 — 긴 계산을 더 짧게 쓰지 말고, 계산 블록을 대체

시작점은 지난주 B+A+C다. 미사용 정의 제거·계수 계산 정리·중간 등식 생략은 이미 적용돼 있었다. 이번에는 그 이후에도 남아 있던 **fiber 두 점의 차이가 1이라는 증명 블록**을 바꿨다.

기존 블록:
1. 두 점을 각각 basis sum으로 전개.
2. 차원이 다른 Fin index를 cast로 맞춤.
3. bit 값과 첫 계수를 계산.
4. 같은 나머지 합이 상쇄되는 것을 `sum_congr`로 확인.

새 블록:
1. 선행 정리 `qMap_total_fiber_one_level_eq`를 두 점에 적용.
2. 두 점은 “첫 basis 벡터의 0배 또는 1배 + 같은 lifted y”임을 사용.
3. 같은 lifted y를 빼고 `get_sDomain_first_basis_eq_1`로 마무리.

즉 **공통 부분 + 1 − 공통 부분 = 1**이라는 구조를 이미 증명된 정리에 맡긴다. 대상 정리 이후의 결과나 대상 정리 자체를 가져오지 않는다. 새 top-level 보조정리는 만들지 않았다.

| ID | 부모 | 변경 | HB | 토큰 | 실제 상태 |
| --- | --- | --- | ---: | ---: | --- |
| c001 | 시작 best | 기존 one-level fiber 정리로 블록 대체 | 미측정 | 981 (정적) | coercion 보조정리 이름·단순화 오류 |
| **c002** | c001 | 올바른 Submodule coercion·Fin 조건 단순화로 수리 | **21,010** | **966** | **3회 통과** |

예산 **2/6** 사용. 수리 전후의 논리적 변환은 동일하며 c001 실패는 그대로 보존했다. 이번 범위에서 큰 개선을 확인했으므로 남은 예산을 채우기 위해 추가 변환을 강제하지 않았다.

[최종 후보](P11/c002/candidate.lean) · [초기 블록 대체 diff](P11/c001/parent.diff) · [수리 diff](P11/c002/parent.diff).

재사용 근거:
- 고정 ArkLib `ArkLib/ProofSystem/Binius/BinaryBasefold/Prelude.lean:256–267`: `qMap_total_fiber_one_level_eq`. 대상은 815행이므로 선행 선언이다.
- 기존 dependency `CompPoly/Fields/Binary/AdditiveNTT/Domain.lean:471–475`: `get_sDomain_first_basis_eq_1`.
- 최종 대상 공리는 원본과 동일한 `propext`, `Classical.choice`, `Quot.sound`. 재사용한 정리의 증명도 이 검사를 통해 대상 의존성으로 확인했다.

**17,327 HB와 413토큰의 추가 감소**는 이 블록 교체 전체의 결과다. cast·bit·sum 중 어느 내부 단계가 몇 HB였는지는 측정하지 않았다. 라이브러리 정리 재사용은 전체 라이브러리를 재빌드하는 비용을 포함하는 실험이 아니라, 기존 의존성을 사용하는 대상 proof 계측이다. 다른 theorem/dependency 환경에서는 같은 보조정리가 없거나 bridging cost가 커질 수 있다.

## 작은 파일럿과 비교해 무엇을 배웠나

앞선 원본 출발 파일럿은 P11의 작은 단일 변경을 분리해 S1 4.07%, S2 1.73% HB 감소, S3 0.65% HB 증가를 확인했다. 이번에는 더 넓은 변경 범위를 허용해 두 문제에서 큰 추가 개선을 찾았다.

다만 시작 proof, 후보 수, 탐색 방식이 다르다. 따라서 “큰 구조 전략이 작은 전략보다 N배 우수하다”는 공정한 정책 비교는 아니다. 이번 근거가 지지하는 것은 **작은 변경만 반복하는 탐색 범위로는 큰 개선 기회를 놓칠 수 있다**는 설명이다.

- P8: 재귀·귀납 구조와 증거 조립 방식을 함께 검토.
- P11: 긴 계산을 부분적으로 줄이기 전에 동일 결론을 제공하는 기존 정리부터 탐색.
- 공통 절차: 바꿀 블록의 입력·출력을 명확히 하고, 비용을 숨기지 않은 전체 proof로 검증·계측.

## 검증 범위와 운영 이력

- Lean v4.31.0, 기존 cslib `8ea71c8df91acd63285515a04da952b23b78d266`, ArkLib `c1712f6c496d0aef04f09bae42aec13811b3273f`.
- 명제·주변 파일·imports/options 유지. 원본 선언을 유일하게 교체하여 전체 파일 컴파일 후 대상 공리를 확인.
- 기존 설치만 사용. 설치·다운로드·의존성 빌드·대시보드 제출 없음.
- 실행 전후 fingerprint 및 후보 해시 검사. 최초 실행 후 실행기 수정 없음.
- P8 원본 공리는 표준 세 공리, 시작점·성공 후보 모두 공리 없음. P11 성공 후보는 원본과 같은 표준 세 공리.
- P8: 원본/시작점/성공 후보 5개 × 3회 = **21회 통과**, 실패 후보 1회.
- P11: 원본/시작점/성공 후보 1개 × 3회 = **9회 통과**, 실패 후보 1회.
- 전체 **30회 통과 + 2회 컴파일 실패**. 실패 실행에는 HB 계측을 수행하지 않았다.
- 실험 전체 API 비용은 미집계이며 대회 API 예산 준수를 주장하지 않는다.
- 멀티에이전트 준비·독립 실행기 검토가 반복된 도구 호출 오류로 완료되지 않았다. P8 첫 두 후보의 정적 독립 검토 이후 나머지 준비·실행은 주 세션에서 수행했다. 독립 실행기 감사 완료로 표현하지 않는다. mock 테스트 13개, 기존 회귀 테스트 36개 통과를 보조 근거로 사용했다.
- `review.json`의 passed는 자동 사후 검사이며 독립 에이전트 검토 완료 표시가 아니다.
- 세 반복의 동일 값은 다른 머신·버전 재현성이나 통계적 유의성 증명이 아니다. 전체 transitive cache를 고정한 hermetic build도 아니다.
