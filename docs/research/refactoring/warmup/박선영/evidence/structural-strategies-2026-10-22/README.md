## 질문과 범위

수학 분야가 달라도 공통된 증명 구조를 찾아 적용하는 변환이 heartbeat를 줄이는가? 어떤 조건에서는 적용할 수 없거나, 검증에 실패하거나, 비용이 증가하는가?

P11에서 확인한 단일 정리의 효과를 일반 성능으로 해석하지 않는다. 이번에는 구조적 단서에 따른 적용 판단을 먼저 기록하고 여러 정리에서 시험한다. heartbeat가 주 지표이고 proof body 토큰 수는 보조 지표다. 유효성은 필수 조건이다. 에이전트의 전략 선택 성능을 입증하는 실험이나 공식 점수 평가가 아니다.

- 기존 Warm-up 원본을 사용한다. 다른 사람의 선택 후보를 원본으로 취급하지 않는다.
- 정리별 원본에서 각 전략을 독립 적용한다. 첫 묶음에서는 전략을 누적하지 않는다.
- 정리 번호를 고르기 전에 관찰한 구조와 적용 근거를 남긴다. 적용 구조가 없는 사례도 보존한다.
- 이 문서는 준비 기록이다. 빈 결과 JSON, 미래 실행 폴더, 복제한 원본 파일은 만들지 않는다.

## 전략 v1

### S1 — 불필요한 지역 요소 하나 제거

- **단서:** 지역 `let`·`have`·`set`이 이후 명시적 참조에 나타나지 않거나, 나머지 증명 경로에 필요하지 않아 보인다. `set`도 지역 별칭 도입으로 포함하되 목표의 표현식을 바꾸는 효과를 함께 확인한다.
- **변환:** 해당 선언 하나와 그 선언에만 속한 본문을 제거한다. 동시에 다른 전술로 바꾸지 않는다.
- **가설:** 불필요한 선언의 elaboration을 생략하면 비용이 줄 수 있다.
- **주의:** 이름이 안 보인다고 미사용이 확정되는 것은 아니다. `simp_all`, `aesop`, 타입 클래스 탐색, 지역 인스턴스, 의존 타입, 익명 가정의 사용을 확인한다. 지역 문맥이 달라져 자동화 비용이 늘 수도 있다.
- **제외:** 정리 밖의 정의·가정·import 변경, 필요한 사실을 다른 보조정리로 대체하는 변경.

### S2 — 중간 등식 하나 생략

- **단서:** `calc`에 같은 목적지로 직접 연결할 가능성이 있는 중간 등식이 있다. 단순히 `calc`가 길다는 이유로 적용 가능하다고 판정하지 않는다.
- **변환:** 하나의 중간 등식 노드를 없애고 인접 두 연결을 하나로 바꾼다. 필요한 연결 전술은 기록하되 다른 블록까지 재작성하지 않는다.
- **가설:** 중간 표현식과 등식 연결의 elaboration을 줄일 수 있다.
- **주의:** 중간 식이 타입·강제 변환 추론을 돕거나 자동화의 탐색 범위를 줄였을 수 있다. 생략으로 비용이 늘거나 검증에 실패할 수 있다.
- **제외:** 마지막 계산 블록 전체를 새 대수 알고리즘으로 바꾸는 변경. 이는 별도 전략이다.

### S3 — 동일한 반복 추론 재사용

- **단서:** 여러 위치에서 동일하거나 동일 인자로 인스턴스화할 수 있는 명제·계산을 반복한다. 전술 이름이 같은 것만으로는 부족하다.
- **변환:** 가장 가까운 공통 scope에서 지역 사실 하나를 증명하고 반복 위치에서 재사용한다.
- **가설:** 반복되는 증명 탐색·계산을 한 번으로 줄일 수 있다.
- **주의:** 분기별 가정이 다르면 같은 명제가 아닐 수 있다. 새 보조 사실의 일반화·인자 추론·대입 비용 때문에 악화할 수도 있다.
- **제외:** 기존 정리 호출로 전체 증명을 대체하기, 전역 보조정리 추가, 서로 다른 사실을 무리하게 하나로 일반화하기.

## 첫 실행의 통제 조건

1. 각 후보 작성 전에 원본 SHA-256, 전략 ID, 대상 블록, 적용 판단 근거, 단일 변경 가설을 기록한다.
2. 명제·binder·가정·import·option·주변 선언은 고정한다. 전체 원본 파일에 대상 proof를 교체해 검증한다. 대상 정리를 이미 포함하는 빌드 산출물을 import하는 것만으로 검증하지 않는다.
3. 정리별 버전·upstream revision·manifest·검증기·토크나이저·계측 방법을 고정하고 같은 조건에서 원본과 후보를 비교한다. 모든 정리가 같은 Lean 버전을 쓸 수 있다고 가정하지 않는다.
4. 대상 공리 목록이 정상 출력됐는지 확인하고 원본 대비 새 공리 및 `sorryAx`를 허용하지 않는다. 주변 파일의 경고와 대상 정리의 의존성은 구분한다.
5. 적용 가능한 정리×전략당 최초 후보 1개, 실패 시 수정 후보 최대 1개로 제한한다. 수정도 별도 시도이며 같은 전략 범위에 머문다. 적용 불가와 환경 차단은 proof 실패와 구분한다.
6. 원본에서 각 전략을 독립 적용한다. 더 좋은 후보를 찾았더라도 다른 전략의 비교 부모를 바꾸지 않는다. 조합 실험은 후속 단계다.
7. 성공·악화·검증 실패·timeout·환경 오류를 모두 보존한다. 계측 실패나 null HB는 개선으로 집계하지 않는다. 실행 timeout 값은 환경 점검 후 실행 전에 고정한다.
8. HB 절대 차이와 원본 대비 감소율, 토큰 증감을 함께 보고한다. 서로 다른 계측 정의의 숫자를 합쳐 평균내지 않는다. 한 번의 측정으로 안정성을 주장하지 않으며, 작은 차이를 채택하기 전에는 같은 절차로 원본·후보를 재측정하고 반복값을 모두 남긴다.

첫 6개는 규칙을 다듬는 **탐색용 사례**다. 이미 읽은 원본을 미노출 평가 표본이라고 부르지 않는다. 후속 일반화 확인은 적용 규칙을 고정한 뒤 별도 정리에서 수행한다. 표본 선정 자체도 구조와 환경 가용성에 따른 편향이 있음을 명시한다.

## 기록과 판정

| 시점 | 기록 항목 |
| --- | --- |
| 후보 작성 전 | 정리, 원본/문맥 식별자와 해시, 전략 버전, 대상 위치, 적용 판단과 근거, 예상 효과 |
| 실행 전 | 후보와 해시, 원본 대비 diff, 환경·검증기·계측 설정, timeout·시도 예산 |
| 실행 후 | 전체 파일 검사, 대상 공리, 원시 로그, HB·토큰, 실행 상태 |
| 해석 | 관측된 개선/악화, 원인 추정, 반례 조건, 후속 확인 |

적용 상태는 `적용 구조 없음 / 불확실 / 적용 후보 있음`으로 기록한다. 실행 뒤에는 `검증 실패 / 계측 불가 / 검증·계측 성공`을 구분하고, 성공한 경우에만 `개선 / 동일 / 악화`를 판정한다. 아직 실행하지 않은 경우 결과는 **미실행**이다.

관측과 원인 추정을 구분한다. HB 감소는 특정 tactic이 병목이었다는 증거가 아니다. S1/S2/S3 중 하나가 일부 사례에서 성공해도 전체 증명에 우선 적용해야 한다는 결론으로 확대하지 않는다.

## 기존 실행기와 다음 구현 경계

[기존 실행기](../run_experiments.py)는 `problem()`과 CLI에서 P8/P11만 지원한다. 다른 번호를 넘겨 바로 실행할 수 없다. 전체 파일 교체·검증·계측 로직은 재사용 후보지만 다음 확인이 필요하다.

- 원본 선언이 지정 revision의 소스에 정확히 한 번 존재하는지, namespace·`module`·`omit` 문맥을 처리하는지.
- 선택 문제의 환경이 준비돼 있는지. 벤치마크에 버전이 기재됐다는 사실과 로컬 설치·실행 가능 여부는 다르다.
- 기존 `valid_check()`는 허용 공리 집합을 검사한다. 이번 설계의 **원본 대비 새 공리 없음**은 별도 비교가 필요하며 이미 제공한다고 가정하지 않는다.
- `evaluate(..., output_dir=...)`로 과거 발표 집계 밖에 새 실행을 분리할 수 있다. 기존 선택 proof·측정 JSON·로그·snapshot은 수정하지 않는다.

다음 단계는 선정표의 불확실한 문맥 확인과 환경 가용성 점검, 필요한 최소 adapter 확장이다. 코드 수정 범위와 실행 예산을 정한 뒤 후보 작성·측정으로 넘어간다. 이번 준비 단계에서는 검증기 수정, Lean 실행, toolchain 다운로드, 유료 API 호출, commit/push를 하지 않았다. 로컬 skill은 공유하지 않는다.
