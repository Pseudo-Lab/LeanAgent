# 담당 3·6·13번: 증명 리팩터링 전략과 인사이트

작성: 권주원 · 초안 v0.1 · 기준일: 2026-10-09 · 공유 예정: 2026-10-11(일)

담당 세 문제의 개요, 리팩터링 과정과 검증 결과를 정리한다. 현재 확인된 후보의 증명 토큰 합계는 **3,210 → 799, 원본 대비 75.11% 감소**했다. 세 문제 모두 지정된 환경에서 같은 후보 코드로 컴파일과 대상 공리 검사를 통과했다.

## 3. 어떻게 리팩터링했는가

### 3번: 단계별 교환을 전체 교환 정리로 바꾸기

**문제 이해.** 이미 정의된 x의 값을 바꾸는 갱신과, 아직 비어 있는 y에 내용을 처음 저장하는 초기화를 생각하면 된다. 두 순서 모두 최종적으로 x와 y에 같은 내용이 저장되어야 한다. 여기서 `UpdateState`는 두 상태 사이의 관계이고, `updatedState`는 새 상태를 만드는 함수다.

**원본의 논리.** `induction Hup`으로 갱신 관계의 구조를 따라간다. 빈 갱신을 처리하고, 첫 변수의 갱신과 나머지 갱신을 나눠 초기화와 교환한다. 각 단계에서 초기화·갱신의 유효성과 변수들이 겹치지 않는다는 조건을 확인한다.

**바꾼 논리.** 초기화할 변수들이 처음 상태에서도 미정의임을 확보한다. 갱신할 변수는 이미 정의되어 있으므로 두 목록은 겹칠 수 없다. 초기화를 먼저 한 중간 상태를 제시하고, 실행 관계를 함수식으로 바꿔 기존 목록 교환 정리를 적용한다. 그 뒤 갱신도 유효함을 보인다.

핵심은 실제 증명에 들어 있는 다음 두 줄이다.

```lean
unfold updatedStates
rw [updatedStatesComm]
```

**관찰.** `unfold updatedStates`를 삭제하면 더 짧아 보이지만, 교환 정리는 내부 함수 `updatedStates'`에 대한 정리라 목표에 맞는 식을 찾지 못했다. 이 두 단어는 불필요한 설명이 아니라 목표와 정리를 연결하는 단계였다.

**인사이트.** 직접 귀납법을 더 짧게 쓰는 것보다, 전체 구조를 처리하는 정리를 재사용하는 변화가 컸다. 귀납법 자체가 없어지는 것은 아니다. 재사용하는 교환 정리 안에도 귀납법이 들어 있다.

### 6번: 귀납과 반복되는 대수 계산을 공유하기

**문제 이해.** time ordering은 연산자들을 시간 순서 조건에 맞춰 정렬하는 과정이다. supercommutator는 부호를 포함하는 교환자다. 두 연산자가 양방향 시간 순서 관계를 만족할 때, 임의의 주변 대수 원소 a와 b 사이에 있는 교환자를 앞으로 옮겨도 `ι`로 보낸 결과가 같음을 증명한다. 이 문맥에서는 같은 시간의 연산자들을 다루는 조건으로 사용한다.

```text
설명용 표기: ι(T(a · [φ, ψ]ₛ · b)) = ι([φ, ψ]ₛ · T(a · b))
```

**원본의 논리.** 두 대수 원소에 대한 중첩 귀납과 긴 대수 계산을 수행한다. `[φ, ψ]`, `[ψ, φ]`, 빈 목록의 경우에 비슷한 정렬 분해가 반복된다.

**바꾼 논리.** `Submodule.span_induction₂`로 두 원소에 대한 귀납을 함께 처리한다. 공통 정렬 결과와 좌우 블록을 한 번 정의하고, 지역 보조 정리 하나를 세 목록에 적용한다. 나머지 부호·분배 계산에는 필요한 재작성과 단순화 규칙을 지정한다.

```lean
induction Basis.mem_span ofCrAnListFBasis a, Basis.mem_span ofCrAnListFBasis b using
  Submodule.span_induction₂
```

**관찰.** 더 짧은 445토큰 후보는 14,638 heartbeat였고, 선택한 450토큰 후보는 14,133이었다. 또 `rw`를 `simp only`로 바꾼 후속 시도는 `smul_comm`의 반복 재작성으로 최대 재귀 깊이에 도달했다.

**인사이트.** 반복 계산을 보조 정리로 공유하는 것이 길이와 비용을 함께 줄였다. 교환법칙을 사용할 때는 재작성 방향도 중요하다. 더 짧은 자동화 호출이 더 적은 작업을 한다고 볼 수 없다.

### 13번: 정수 수열을 유한 상태로 표현하기

**문제 이해.** 정수 수열 u가 일정한 구간 안에 있고, n ≥ 4에서 직전 네 항으로 다음 항을 결정하는 점화식을 만족한다고 가정한다. 원문에는 분모가 0이 아니라는 조건도 있다. 목표는 어떤 N 이후 양의 주기 c에 대해 `u(n+c) = u(n)`이 되는 것이다.

**핵심 수학.** 한 항만으로는 다음 항을 결정할 수 없지만, 연속 네 항을 묶으면 다음 상태가 결정된다. 각 항이 유계 정수이므로 네 항 묶음의 가능한 상태도 유한하다. 같은 상태가 두 번 나오면 그 뒤의 항들도 같아져 주기적 반복으로 이어진다.

**바꾼 논리.** 상태를 `Fin 4 → Set.Icc B T`로 표현하고, 처음부터 `i < j`인 동일 상태를 주는 비둘기집 정리를 사용한다. 찾은 두 인덱스의 대소를 다시 나누는 과정을 없앤다. 이후 강한 귀납법에서 직전 네 항의 인덱스를 맞추는 보조 정리를 좁히고, 주기를 `j − i`로 잡는다.

```lean
let f : ℕ → (Fin 4 → Set.Icc B T) := fun n k => ⟨u (n + k), hB (n + k)⟩
```

**후속 개선.** 실수로 옮긴 두 정수의 등식을 원래 정수의 등식으로 연결할 때, 타입을 명시한 `apply @Int.cast_injective ℝ _ _`를 사용해 260 → 259토큰으로 줄였다. 수학적 구조는 같고 scaled heartbeat도 같다. 타입을 충분히 지정하지 않은 다른 시도는 실패했다.

**인사이트.** 좋은 상태 표현과 원하는 형태의 결론을 바로 주는 정리 선택이 효과가 컸다. 이후 한 토큰을 줄인 변화는 별도의 작은 개선이다. 원문의 분모 비영 가정은 증명에서 직접 사용하지 않더라도 명제를 보존하기 위해 그대로 유지했다.

## 4. 세 문제에서 얻은 공통 인사이트

1. **수학적 구조를 바꾸는 개선이 컸다.** 전체 목록 교환, 두 원소의 공동 귀납, 네 항의 유한 상태 표현이 각각 긴 증명 구조를 줄였다.
2. **정리가 목표에 맞도록 표현을 정리해야 한다.** 3번의 unfold, 6번의 공통 블록 분해, 13번의 인덱스 정리는 기존 정리를 적용하기 위한 연결 단계다.
3. **짧은 증명과 저렴한 증명을 함께 봐야 한다.** 3번의 86토큰 대안은 4.26.0에서 311 heartbeat로, 90토큰 후보의 164보다 컸다. 6번에서도 445토큰보다 450토큰 후보를 선택했다.
4. **이름 단축과 구조 개선은 다르다.** 세 문제의 지역 이름을 줄여 본문 총 91자를 추가로 줄였지만 당시 토큰 합계 800과 scaled heartbeat는 그대로였다. 문자 수 감소를 평가 지표 개선으로 주장하지 않는다.
5. **측정 문맥이 결과에 영향을 준다.** 13번을 한 Lean 프로세스에서 반복 측정하면 뒤의 선언에 캐시 효과가 나타났다. 비교에는 독립 프로세스 결과를 사용했다.
6. **실패와 후보 유지도 탐색 결과다.** 컴파일 실패나 더 나쁜 비용을 낸 시도는 최종 성능에서 제외하고, 기존 후보를 유지한 이유를 기록한다.
