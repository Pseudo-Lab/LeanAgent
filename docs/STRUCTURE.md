# docs 폴더와 파일명 지침

LeanAgent의 발표·연구 자료를 작성하거나 정리하는 사람과 에이전트가 따라야 할 공통 규칙입니다. `docs/` 작업을 시작할 때 이 문서와 대상 폴더의 README를 먼저 확인합니다. 경로·파일명·목차 규칙은 이 문서를 기준으로 적용하고, 규칙을 변경할 때도 이 문서를 갱신합니다.

자료의 위치는 주제와 문제 세트를 기준으로 정하고, 모임 README는 발표자료를 연결하는 목차로 사용합니다. 아래의 `<분야>`, `<세트>`, `<발표자>` 등은 실제 값으로 바꿔 사용합니다.

## 폴더 구조

```text
docs/
├── README.md                              전체 자료 목차
├── STRUCTURE.md                           폴더·파일명 지침
├── meetings/
│   └── YYYY-MM-DD-topic/
│       └── README.md                      해당 모임 발표자료 링크
└── research/
    ├── README.md                          분야별 자료 목차
    ├── papers.md                          공통 논문 목록
    ├── <분야>/
    │   ├── README.md                      분야별 공유 자료 안내
    │   └── <발표자>/                      논문 조사·학습 자료
    └── refactoring/
        ├── README.md                      문제 연구 안내
        ├── arena-guide.html               개발·환경·대시보드·데이터 출처·에이전트 실험 통합 안내
        ├── evidence/corpus-deep-dive/      공통 출처 분석 결과·재현 코드·검증 기록
        ├── evidence/agent-reproducibility/ effort 비교·반복 실험·하네스 검증 근거
        └── <세트>/
            ├── README.md                  세트별 담당자·자료 안내
            └── <발표자>/                  문제 발표·보고서·검증 기록
```

분야 폴더는 `lean-mathlib`, `autoformalization`, `automated-theorem-proving`, `verifier-guided-agent`를 사용합니다. 발표자 폴더는 담당 배정표의 한글 이름을 사용합니다.

Warm-up의 세트 이름은 `warmup`입니다. 여러 주차에 걸쳐 같은 문제를 보완할 수 있으므로 `refactoring` 안에 주차 폴더를 추가하지 않습니다. 한 발표에서 여러 문제를 다루면 발표자별 묶음을 유지하고, 문제별 증명·로그를 그 안에서 구분합니다. 날짜·문제 번호·검증 환경은 README와 본문에 기록합니다.

## 자료별 저장 위치

아래 경로는 저장소 루트 기준입니다. 기존 분야·세트·발표자 폴더가 있으면 재사용하고, 같은 대상을 다른 철자나 약칭으로 중복 생성하지 않습니다.

| 자료 유형 | 저장 위치 |
| --- | --- |
| 대회용 에이전트 공통 설계·개요 | `docs/research/refactoring/<주제>.html` 또는 `<주제>.md`; Refactoring 목차에서 연결 |
| 논문 조사·분야별 발표 | `docs/research/<분야>/<발표자>/` |
| Warm-up 발표·문제 풀이 | `docs/research/refactoring/warmup/<발표자>/` |
| 다른 문제 세트의 연구 | `docs/research/refactoring/<세트>/<발표자>/` |
| 대회 공통 도구 사용·운영 안내 | `docs/research/refactoring/<도구>.md` 또는 `<도구>.html` |
| 증명·실험·검증 근거 | 해당 발표자 폴더의 `evidence/` |
| 별도 학습 기록 | 해당 발표자 폴더의 `studies/<주제 또는 날짜>/` |
| 모임별 발표 목차 | `docs/meetings/YYYY-MM-DD-topic/README.md` |

분야·세트 이름은 소문자 영문과 하이픈을 사용합니다. 날짜는 `YYYY-MM-DD` 형식으로 적습니다. 발표자 폴더명에 날짜·주차·문제 번호를 붙이지 않습니다.

Arena 에이전트 개발 개요, 문제별 환경 고정 가안, 대시보드 운영 안내, 데이터 출처·후보군 분석과 서브에이전트 effort·재현성 실험은 [통합 가이드](research/refactoring/arena-guide.html)에서 관리합니다. 공유 문서는 통합 HTML 하나로 유지하고, 통합 전 개별 문서와 원본 ZIP은 게시하지 않습니다. 공통 출처 분석의 결과 JSON·재현 코드·기존 검증 기록은 `research/refactoring/evidence/corpus-deep-dive/`에 보관하고, 복사 출처와 파일 해시는 같은 폴더의 `provenance.json`에 기록합니다. 에이전트 실험의 조건·측정 원문·최종 증명·기록 재생 코드는 `research/refactoring/evidence/agent-reproducibility/`에 두고, 해당 폴더의 `provenance.json`에 포함·생략 범위와 원본 해시를 기록합니다.

## 파일명

| 이름 | 용도 |
| --- | --- |
| `README.md` | 작성자·주제·문제 번호·대표 자료·근거 자료 안내 |
| `presentation.html` | 대표 HTML 발표·학습 자료 |
| `report.md` 또는 `report.html` | 대표 상세 보고서·논문 조사 문서. 기존 형식 유지 |
| `metrics.json` | 대표 측정 기록. 측정일·환경·출처를 내부에 기록 |
| `evidence/` | 원본·후보 증명, 실패 시도, 로그, 버전별 결과, 재현 스크립트 |
| `outline.md` | 발표 구성안·메모를 보관하는 선택적인 보조 파일 |

발표자 폴더에 README를 두고, 나머지는 실제 자료가 있는 경우에만 추가합니다. 파일명 통일을 위해 빈 발표자료·보고서·측정 파일을 만들지 않습니다.

`evidence/` 아래의 문제 번호·정리 이름·시도 번호는 재현 명령과 대응하도록 유지합니다. MIL 풀이처럼 여러 학습 예제로 구성된 자료는 `mil-ch2/` 등 주제가 드러나는 하위 폴더에 보관할 수 있습니다. 별도 학습 기록은 `studies/<주제 또는 날짜>/`로 구분합니다.

같은 폴더에 독립적인 조사 문서가 여러 개 있으면 대표 문서는 `report.md` 또는 `report.html`로 두고, 추가 문서는 `leandojo.md`처럼 주제가 드러나는 이름을 사용합니다. 파일명 통일을 위해 서로 다른 자료를 덮어쓰거나 합치지 않습니다.

## README 작성 규칙

README는 자료의 위치와 범위를 안내합니다. 발표·보고서 본문을 복제하지 않고 실제 파일로 연결합니다. 링크는 해당 README 기준의 상대 경로를 사용하며, 개인 컴퓨터의 절대 경로를 넣지 않습니다.

### 발표자 README

제목은 `# <발표자> <분야 또는 세트·문제 번호>`로 작성합니다. 다음 항목을 순서대로 포함합니다.

1. 자료 범위: 다루는 주제 또는 문제 번호와 공유일·모임.
2. 대표 자료: 발표자료, 또는 발표파일이 없을 때 사용할 공유 문서.
3. 상세·근거 자료: 보고서, 측정 기록, 증명·로그 등 실제 존재하는 자료.
4. 관련 자료: 다른 분야·세트·학습 기록과 연결할 필요가 있을 때만 추가.

작성 틀은 아래와 같습니다. 꺾쇠괄호 부분을 실제 내용으로 채우고, 자료 항목에는 상대 링크를 넣습니다. 없는 자료의 항목은 삭제합니다.

```markdown
# <발표자> <분야 또는 세트·문제 번호>

<공유일·모임>. <자료의 주제와 범위>.

- 발표자료: <대표 파일 상대 링크>
- 상세 보고서: <보고서 상대 링크>
- 측정 기록: <metrics.json 상대 링크>
- 검증 근거: <evidence/ 상대 링크>
- 관련 자료: <관련 README 또는 문서 상대 링크>
```

검증 상태를 안내할 때는 확인된 범위만 적습니다. 계획·미검증 후보·검증 완료 결과를 구분하고, 상세 환경과 재현 절차는 보고서나 근거 자료에서 확인할 수 있게 연결합니다.

### 분야·세트 README

분야 README는 `발표자 | 주제 | 대표 자료 | 자료 폴더`, 문제 세트 README는 `발표자 | 문제 | 대표 자료 | 자료 폴더` 열의 표를 사용합니다. 대표 자료는 파일에 직접 연결하고, 자료 폴더는 발표자 README에 연결합니다. 한 파일이 여러 범주를 포함하면 대표 자료의 설명에 그 범위를 표시합니다.

### 모임 README

모임 폴더에는 README만 두고 대표 발표자료를 직접 연결합니다. 발표파일이 없는 경우 원래 공유된 MD 문서를 연결하고 문서 형식을 표시합니다.

제목은 `# LeanAgent <모임명>`으로 쓰고, 모임 일시와 공유 주제를 짧게 적습니다. Warm-up과 논문 조사를 함께 공유하는 모임은 `발표자 | 문제 | Warm-up 발표자료 | 논문·학습 발표자료` 열의 표를 사용합니다. 다른 모임은 발표 주제에 맞게 자료 열을 조정합니다. 자료가 없으면 링크 대신 `자료 없음`으로 표시합니다.

구성안·보조 보고서·학습 노트·측정 JSON·실험 로그는 모임 목차에 나열하지 않습니다. 자세한 자료는 분야·세트·발표자 README에서 안내합니다. 구성안 링크는 공유용 README에 노출하지 않으며 파일은 보조 자료로 보관합니다.

모임 README는 각 발표자의 파일 위치가 정리된 뒤 마지막에 갱신합니다.

## 혼합 자료와 중복

문제 연구와 논문 조사가 같은 발표파일에 있으면 주된 용도의 폴더에 원본 하나를 두고, 다른 분야에서 상대 링크로 연결합니다. 발표 흐름을 임의로 분할하거나 동일한 HTML 사본을 여러 폴더에 만들지 않습니다.

양쪽 발표자 README에 해당 파일이 다루는 범위를 설명하고, 모임 표에서 같은 파일을 연결할 때는 `같은 발표자료`라고 표시합니다. Warm-up과 논문 조사의 혼합 여부는 [Refactoring 안내](research/refactoring/README.md#공유-파일의-warm-up논문-조사-혼합-여부)에도 반영합니다.

내용이 같은 사본을 통합할 때는 먼저 동일한 파일인지 확인하고, 한 원본 위치로 모든 링크를 갱신합니다.

## 에이전트 작업 순서

1. 이 지침, 대상 폴더의 README, 현재 Git 변경 사항을 확인합니다. 사용자가 수정 중인 내용을 보존합니다.
2. 자료를 분야 연구·문제 연구·학습 기록으로 분류하고, 기존 파일과 중복되거나 여러 범주를 함께 담는지 확인합니다.
3. 저장 위치와 대표 파일을 정한 뒤 요청받은 범위의 자료를 작성·수정·이동합니다. 요청 범위 밖의 자료까지 일괄 재구성하지 않습니다.
4. 발표자 README와 분야·세트 목차를 갱신합니다. 새 분야·세트를 추가했다면 상위 목차에도 연결합니다.
5. 이동한 파일을 참조하는 Markdown·HTML 링크, 이미지·스크립트 경로, 안내 문서의 재현 명령을 갱신합니다.
6. 대표 자료가 확정되면 마지막에 해당 모임 README를 갱신합니다.
7. 아래 완료 기준을 확인하고, 확인하지 못한 항목이 있으면 작업 결과에 명시합니다.

경로 정리만 하는 경우 증명 코드·측정 JSON·원시 로그의 내용은 보존합니다. 기록에 포함된 과거 실행 경로는 당시의 근거로 유지합니다. 검증된 증명과 미검증 후보, 설명용 데모와 실측 결과를 구분합니다.

## 완료 기준

- [ ] 자료가 정해진 분야·세트·발표자 경로에 있고, 동일한 자료의 불필요한 사본이 없다.
- [ ] README에 자료 범위와 실제 존재하는 대표·근거 자료가 연결되어 있다.
- [ ] 모임 README에는 대표 공유 자료만 연결되어 있고, 공유용 README에 구성안 링크가 없다.
- [ ] 수정한 문서의 상대 링크·앵커·이미지·스크립트 경로와 이동된 파일을 가리키는 링크가 유효하다.
- [ ] HTML을 추가·수정·이동했다면 브라우저에서 자료가 열리고 발표 탐색과 자산 로딩이 동작한다.
- [ ] 경로만 정리했다면 증명·측정·로그 내용이 보존됐다. 증명이나 실행 코드를 수정했다면 해당 환경에서 검증하고 결과를 기록했다.
- [ ] `git diff --check`를 통과하고, 의도하지 않은 파일 변경이나 누락이 없다.
